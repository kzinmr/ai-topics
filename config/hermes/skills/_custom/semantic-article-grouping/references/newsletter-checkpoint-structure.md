# Newsletter Checkpoint JSON Structure

The `newsletter-ingest` pipeline saves its output to `${HERMES_HOME}/cron/data/newsletter/latest.json`. The actual on-disk structure differs from the `candidates[]` display format shown in the cron kickoff "Script Output" section.

## Actual On-Disk Structure

```json
{
  "ok": true,
  "run_id": "20260713T071112Z",
  "collected_at": "2026-07-13T07:11:12Z",
  "processed_count": 4,
  "processed_messages": [
    {
      "message_id": "<20260712123214...>",
      "subject": "How tech workers actually feel about AI in 2026",
      "date": "2026-07-12",
      "source_label": "uid=358",
      "raw_path": "wiki/raw/newsletters/2026-07-12-how-tech-workers...md",
      "article_count": 20,
      "articles": [
        {"title": "Link 1", "url": "https://substack.com/redirect/2/eyJ..."},
        {"title": "Link 2", "url": "https://substack.com/app-link/post?..."}
      ]
    }
  ],
  "checkpoint_path": "...",
  "archive_path": "..."
}
```

## Key Differences from the Display `candidates[]` Format

| Aspect | `candidates[]` (Script Output) | `processed_messages[].articles[]` (On Disk) |
|--------|-------------------------------|---------------------------------------------|
| Top-level key | `candidates` | `processed_messages` |
| Per-item fields | `item_id`, `source`, `source_name`, `title`, `url`, `raw_path`, `message_id`, `date` | Only `title`, `url` |
| Grouping | Flat array — each link is independent | Nested — links are grouped by parent message |
| Batch info | Spread across items | Each msg has `subject`, `date`, `source_label`, `raw_path` |

## How to Process (Python Pattern)

```python
checkpoint = json.load(open(checkpoint_path))
messages = checkpoint.get("processed_messages", [])

for msg in messages:
    subject = msg.get("subject", "")
    raw_path = msg.get("raw_path", "")
    articles = msg.get("articles", [])
    for i, art in enumerate(articles):
        item_id = f"{msg['message_id'][:30]}-{art['title'].replace(' ', '_')[:20]}"
        url = art["url"]
```

## Noise-Check Ordering (Critical)

When iterating over `articles[]`, check noise patterns FIRST. The display format gives no metadata about link types — classification must be by URL patterns alone.

**Correct order** (validated 2026-07-13: wrong order → 5 duplicate takes):
1. `redirect/2/eyJ...` → OAuth redirect (skip)
2. `submitLike`, `comments`, `action=share`, `action=restack`, `@username` → Substack UI (skip)
3. `play_audio`, `play_card` → Audio chrome (skip)
4. `redirect/<uuid>` pattern → UUID redirect (skip)
5. `redirect=app-store` → App store redirect (skip)
6. `post-email-title` → Newsletter post URL (take/reference)
7. Remaining unclassified → skip

**Wrong order** — checking "post-email-title" or "post_id" before noise produces false positives because noise links (like/share) often contain the same `post_id` parameter.

## Why the Script Output Shows Different Data

The "Script Output" at cron kickoff is generated by a pre-run script (`newsletter_checkpoint.py`) that transforms `processed_messages[].articles[]` into a flat `candidates[]` array with augmented fields. This is for human readability. `candidates` is NOT a valid key in the actual checkpoint file. Always write triage scripts against the on-disk structure.
