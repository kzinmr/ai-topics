# Daily RSS Triage Workflow

End-to-end pipeline for processing daily RSS scans, triaging articles, and ingesting wiki-worthy content.

## Prerequisites

- `blogwatcher-db` skill loaded (database queries)
- `semantic-article-grouping` skill loaded (triage criteria)
- Pre-run script has already executed blogwatcher scan, queried DB, read newsletter, listed existing topics

## Workflow

### Phase 1: Report Generation

1. Parse script JSON output for scan results
2. Generate Japanese summary report (scan stats, failed blogs, articles list, Reddit highlights, newsletter info)
3. Save to `~/ai-topics/inbox/rss-scans/daily-scan-YYYY-MM-DD.md`
4. If article_total > 0 but ≤3 are AI-relevant, supplement with web_search (see Low-Article Day Fallback below)
5. If article_total == 0 AND no newsletter → `[SILENT]`

5. Nav-heavy sites (claude.com, research.meta.ai) return navigation menus in the first ~2500 chars of stripped text — the article body follows the page title; read past the menu.
6. **urllib + Chrome UA can still return gzip-encoded bytes (VERIFIED 2026-10-28)**: deepmind.google (and likely other Google-served pages) returned HTTP 200 with a gzip-compressed body that the naive `r.read().decode('utf-8','replace')` recipe wrote out as binary garbage — the fetch script reported OK/len>5000 so the failure was silent. Fix: always add `Accept-Encoding: gzip` handling in the fetcher — `raw = r.read(); if r.headers.get('Content-Encoding')=='gzip' or raw[:2]==b'\x1f\x8b': raw = gzip.decompress(raw)` before decode. Cheap post-fetch guard for batch scripts: grep the saved text for the expected article opening phrase (assert/find the start marker) and treat a miss as FAIL, not OK.

### Phase 1.5: Newsjacking Triage Filter (READER perspective)

Before detailed triage, apply Newsjacking lens (from Elvis Sun's framework) to identify high-signal articles:

1. **Trend Surfing**: Does the article ride an existing wave? (e.g., Claude Code launch, new model release, viral AI tool)
2. **Polarizing Promise**: Does it make a bold, debatable claim that creates curiosity? ("X is dead", "Everyone is wrong about Y")
3. **Contrarian Insight**: Does it challenge conventional wisdom with data-backed arguments?
4. **Pattern Interrupt**: Is it structurally or topically unusual for its source? (e.g., Karpathy writing about biology, Simon Willison on non-web topics)
5. **In-Group Signal**: Does it use specialized knowledge that creates an "insider" resonance for the target audience (r/LocalLLaMA, AI agent developers)?

**Scoring**: Assign each article a `newsjacking_score` (0-5) based on how many criteria it meets.
- Score ≥ 3: **Priority triage** — flag for immediate wiki ingestion
- Score 1-2: **Standard triage** — normal evaluation
- Score 0: **Low priority** — only ingest if highly relevant to core interests

### Phase 2: Triage

**Cron-mode optimization**: When `execute_code` is blocked (standard in cron jobs — verified 2026-08-20), use this 2-pass pattern:
1. **delegate_task** to a subagent that reads all raw articles and returns a JSON array with `{url, title, summary_2lines, ai_relevance: high|medium|low|none, tags: []}`
2. Use the summary to decide which articles to process, then read individual articles with `read_file`

**Direct curl + terminal Python fallback** (no subagent needed for single-article resolution): `curl -sL <url> > /tmp/page.html` then `python3 /dev/stdin << 'PYEOF' ... PYEOF` to parse HTML. Works for Substack (og metadata + `<article>`/`<div class="body">` extraction) and most static sites. No pipes to interpreters (security scanner blocks `curl | python3 -c`). See `references/web-supplement-fetch.md` for full recipes.

For each article, evaluate:
1. **Already covered?** Check `existing_wiki_topics` list
2. **Substantive?** Not a link dump, not Reddit noise
3. **Relevant?** LLMs, AI agents, coding agents, developer tooling, inference/training, prompt engineering, AI safety, open-source AI
4. **Newsjacking score?** (from Phase 1.5) — higher scores get priority placement

## Key Pitfalls
- **SCHEMA.md tag validation (pre-commit blocker)**: The pre-commit hook validates ALL tags on modified files against `wiki/SCHEMA.md`'s canonical taxonomy (900+ tags). This is the #1 cause of blocked commits in wiki-triage runs. **Prevention**: Before creating ANY new entity/concept page, extract its planned tags and validate each against SCHEMA.md. Use `search_files(pattern="tagname", path="~/ai-topics/wiki/SCHEMA.md")` — if missing, patch the appropriate category line (People-Orgs/Products/Models/AI-Agents/Engineering/Domain-Concepts/Meta) in SCHEMA.md FIRST, then create the entity file. This is step 0 in Phase 3. **Grep whole-word, never substring** — `search_files`/`grep` default to substring, which makes `responsible-scaling` pass a bad pre-check by matching the longer `responsible-scaling-policy`; validate each planned tag with `grep -cw <tag>` (or verify the sibling page's frontmatter) so descriptive/subject tags are checked as strictly as self-name tags (see pitfall below). **Recovery** (if you forgot): `git add wiki/SCHEMA.md` the fixed file, then re-run `git commit`.

- **A new concept page's OWN NAME may not be a SCHEMA tag (VERIFIED 2026-10-21)**: when you create `concepts/foo.md` and tag it `foo` to signal self-reference, `foo` is NOT guaranteed to exist in SCHEMA even when a page named `concepts/foo.md` already lives there — the existing page may use a different tag, or the tag was never added. Real failure: created `concepts/abliterated-model-backdoor.md` with tags including `abliteration`; the pre-commit hook blocked on `abliteration` (not `model-backdoor`, which I had pre-validated) because `abliteration.md` exists as a page but `abliteration` was never in the taxonomy. **Rule: when a page's self-name equals its topic (very common for concept pages), grep SCHEMA for that exact self-name too, not just the *other* subject tags.** Cheapest fix: when the hook fires on commit, `search_files(pattern="tagname", path="~/wiki/SCHEMA.md")` → if absent, `patch` the appropriate Models/AI-Agents category line to append it, `git add wiki/SCHEMA.md`, re-commit. Two tags commonly missing that pass the "obvious" scan: the technique self-name (`abliteration`) and new attack/defense nouns (`model-backdoor`). **Adjacent trap (VERIFIED 2026-11-07, trending-topics run): a "safe-looking" descriptive/subject tag on a NEW concept page blocks the commit even after you pre-validated the self-name tag.** Created `concepts/ai-rd-acceleration-doubling.md`; validated its distinctive tags `metr`/`ai-forecasting`/`ai-risk` (all genuinely absent → minted on Meta line), but tagged the body subject `responsible-scaling` — the hook blocked commit because the canonical token is the **page name** `responsible-scaling-policy`, not the concept word. Distinct from the self-name miss: this is a tag you reach for as ordinary *descriptive vocabulary*, and a plain SCHEMA substring scan MISSES it — `grep -c "responsible-scaling" SCHEMA.md` returns a hit (matching the longer `responsible-scaling-policy`) so it looks present, yet the exact token is absent. Rule: when authoring a concept page's tag list, grep EACH tag with `grep -cw <tag>` (whole-word, not substring) — substring grep is what makes `responsible-scaling`/`legal`/`readability`-class tokens pass a bad pre-check. Cheapest recovery on a single-tag hook fire stays the same: check what tag the SAME-TOPIC sibling page actually uses (`grep -A10 tags: wiki/<sibling>.md`) → swap (`responsible-scaling-policy`, `law`, etc.), no SCHEMA mint. This is the fourth+ instance of the page-name-≠-tag family (`legal`→`law`, `ai-bubble`, `readability`, and now `responsible-scaling`→`responsible-scaling-policy`). **Fourth instance (VERIFIED 2026-10-31, trending-topics run)**: tagged `concepts/ai-bubble-bailout-resolution.md` with `ai-bubble` — a token that LOOKS canonical because `concepts/ai-bubble.md` exists as a page — the hook blocked it; `ai-bubble` has never been in the taxonomy and the sibling page actually uses `economics`/`industry`/`controversy`/`valuation`. Same class as the `legal`→`law` case: page name ≠ tag, and the same-topic sibling's actual frontmatter is the cheapest oracle. **Adjacent trap: a tag can enter a file WITHOUT you typing it** — a concurrent job (active-crawl / blog-wiki-ingest / a sibling subagent) may have appended a tag to an existing page's frontmatter earlier in the day, and your `git add` of that page (for your own section append) then makes YOU own the hook failure for it. Real case: `weight-compiled-computers.md` failed on `emulation`, a tag no job in this run added; fix was removal, not minting, since the tag had no SCHEMA entry and carried no navigation value. Rule: on a single-tag hook fire, check `git diff --staged <page> | grep '^+.*tags:'` to see whether the offending token is yours; if not yours and unminted, remove it rather than adding it to SCHEMA. Same class re-verified 2026-10-25: created `concepts/ai-generated-language-readability.md` tagged `readability` — the plain-English topic noun is NOT inherited from any existing tag or page; the hook blocked commit until `readability` was appended to the Models line. Rule stands: grep SCHEMA for EVERY planned tag including single-word self-names before writing the file. **Third instance 2026-10-28**: tagged `concepts/cruz-v-anthropic.md` with `legal` — a "obviously exists" plain-English word — the hook blocked commit; the canonical tag is `law` (already used by the sibling `concepts/anthropic-copyright-settlement.md`). Cheap recovery when the hook fires on a single tag: check what tag the SAME-TOPIC existing page actually uses (`grep -A10 "tags:" wiki/concepts/<sibling>.md`) and swap rather than adding a near-duplicate to SCHEMA — synonym tags (`legal` vs `law`, `readability` style misses) are better mapped than minted.

- **`wiki/log.md` may have NO top-level `# Wiki Log` header (VERIFIED 2026-10-21)**: the prepend-a-dated-entry pattern (`## [YYYY-MM-DD] ...`) assumes the file already starts with a `# Wiki Log` H1. It does not always — a prior run may have stripped it. When you prepend your entry at line 1 and your script/patch adds a leading `# Wiki Log`, you can end up with zero or two headers. After ANY log prepend, run `grep -c '^# Wiki Log' wiki/log.md` and force it to exactly 1 (add it if 0, remove the dup if 2). **Re-verified 2026-10-25 (trending-topics run)**: the file had NO H1 when the script prepended `hdr + "\n" + entry + log`, producing exactly the two-header failure — the dedupe fix is a one-shot Python filter that keeps only the FIRST `# Wiki Log` line. Build the dedupe INTO the prepend script itself (idempotent: after prepend, remove all but the first header line), never as a separate afterthought step. The watchdog (`wiki-watchdog-fix`) restores it reactively but you should not rely on that. **Dedupe gotcha (VERIFIED 2026-10-28)**: the dedupe loop must strip/match on `ln.strip() == '# Wiki Log'`, not exact `ln == '# Wiki Log'` — log.md carries a second legitimate `# Wiki Log` line lower in the file (above the `_Log of all wiki changes..._` italic intro) and a naive exact-match dedupe counted 3 headers after prepend while missing the real duplicate. Also: the pre-existing lower `# Wiki Log` + intro block means the file can look header-clean at the top yet fail a raw count — the canonical check is "exactly ONE line matching `^#\s+Wiki Log` after strip, at the very top".

- **Duplicate frontmatter fields**: When using `patch` to update YAML frontmatter (e.g., changing `updated:` date), be careful not to introduce duplicate fields. The original file may already have `type: entity` — don't add another one. Read the frontmatter block first before patching.

- **Index stub detection**: `search_files("firstname.*lastname")` on the index may miss existing stubs if the index entry uses a different format (e.g., `**Role** | Professor Emeritus` instead of the person's name). Always also check `search_files(target="content")` for the person's name in the entities directory before creating a new entity page. stubs created by `build_x_wiki.py` or `build_blog_wiki.py` may exist even when `search_files` returns nothing.
- Index filename mismatches: short handles vs full names
1. **Index filename mismatches**: `wiki/index.md` may use short handles (`gpjt`) while you'd expect full names (`gilesthomas-com`). Always check the index first.

2. **Pre-staged files**: Previous cron runs or sessions may have already staged files. Use `git diff --staged` before committing to understand what's changed. **Scope your own `git add` to your own files** (e.g. `git add inbox/rss-scans/daily-scan-YYYY-MM-DD.md`), NOT `git add -A` or blanket `git add wiki/ config/` — other jobs (blog-wiki-ingest, newsletter-wiki-ingest, x-bookmarks-ingest, skill-management, wiki-health) routinely leave concurrent uncommitted changes in `wiki/` and `config/hermes/skills/` that you must not sweep into your commit (verified 2026-08-10: `git status` showed many `M`/`D` skill files + untracked files from other jobs; committing only the scan report kept the history clean).

3. **Duplicate entity creation (VERIFIED 2026-08-17)**: Always search for existing entity files before creating new ones. The same person/company may already have a page under a DIFFERENT filename. **Proven failure mode**: Searching with regex dots (`gary.marcus`, `daring.fireball`) returns 0 results even when `gary-marcus.md` and `daringfireball-net.md` exist. The index uses hyphens, not dots. **Mandatory pre-creation pattern**:
   ```
   # 1. Search index with PLAIN TEXT name (no regex):
   search_files(path="wiki/index.md", pattern="gary marcus", target="content")
   search_files(path="wiki/index.md", pattern="gruber", target="content")
   
   # 2. Use find in terminal for filename glob (search_files file target is unreliable):
   terminal("find ~/ai-topics/wiki/entities -name '*gary*' -o -name '*marcus*' 2>/dev/null")
   terminal("find ~/ai-topics/wiki/entities -name '*gruber*' -o -name '*daring*' 2>/dev/null")
   
   # 3. Check git log for files that may have been deleted:
   terminal("cd ~/ai-topics && git log --oneline -3 -- 'wiki/entities/gary-marcus.md'")
   ```
   **Real failure (2026-08-17)**: Created `garymarcus-com.md` and `martinalderson-com.md` as duplicates when `gary-marcus.md` (424 lines, 43KB) and `martin-alderson.md` (360 lines, 33KB) already existed. Had to `rm` the duplicates and merge into existing files instead. The index had the correct filenames all along — the search regex was wrong.

4. **No content to report**: If `article_total == 0` AND no newsletter exists, respond `[SILENT]` — don't generate empty reports.

5. **Category field is JSON**: In blogwatcher DB, `categories` is a JSON array. Use `LIKE '%\"tag\"%'` for SQL filtering or `json.loads()` in Python.

6. **Published vs discovered dates**: Use `discovered_date` for "when blogwatcher found it", `published_date` for "when article was published" (can be NULL).

7. **`search_files` for wiki directory discovery — partial limitation**: `search_files` returns `{"total_count": 0}` for recursive glob patterns like `~/ai-topics/wiki/**/*.md`. However, for **specific filename pattern checks** in known directories (e.g., `search_files(target='files', pattern='gary-marcus*', path='~/ai-topics/wiki/entities')`), it works correctly. Use `execute_code` with Python `os.walk()` or `pathlib` for full directory traversal. **Cron mode note**: `execute_code` is blocked in cron jobs — fall back to `search_files(target='files')` with specific patterns for entity existence checks.

8. **RSS 429 rate limits**: `r/LocalLLM` and `r/LocalLLaMA` frequently hit HTTP 429. Log failures but do NOT retry immediately — wait for next scan cycle to avoid exacerbating rate limits.

9. **Substack redirect URLs**: Newsletter articles use tracking-heavy Substack redirect URLs (e.g., `substack.com/redirect/UUID`). `web_extract` handles these natively — pass the full redirect URL, do not strip tracking parameters. To discover the actual publication domain, resolve the `open.substack.com` link: `curl -sL -o /dev/null -w '%{url_effective}' https://open.substack.com/pub/{author}/p/{slug}` — this reveals the real domain (e.g., `www.latent.space`). ## GitHub Push Protection on raw/ Security Reports (VERIFIED 2026-09-12)

When ingesting security-incident / attack-report articles into `wiki/raw/articles/`, the article body often contains REAL leaked credentials (API keys, tokens) pasted in code samples. GitHub push protection blocks the ENTIRE push with `GH013: Push cannot contain secrets` (e.g. a `rubygems_…` API key from the rubyhack.ai GemStuffer report). This fires AFTER a successful local commit, so the fix sequence is:

1. Find all secret-looking tokens in the offending raw file: `grep -nE "rubygems_[0-9a-f]{20,}|ghp_[A-Za-z0-9]{20,}|sk-[A-Za-z0-9]{20,}" <file>` (extend the alternation for other vendor prefixes).
2. Replace each with a descriptive placeholder like `rubygems_[REDACTED-REVOKED-API-KEY]` (raw/ immutability is already broken by the redaction — the placeholder text documents why).
3. Recompute the `sha256:` frontmatter over the new body (hash changes after redaction).
4. `git add <file> && git commit --amend --no-edit` (amend, don't new-commit — the secret is in the bad commit, and pushing the same ref still scans all commits being pushed).
5. `git push` again.

Do NOT use the allow-secret URL GitHub offers or `--no-verify`-style bypasses for real tokens; redact. This applies to any incident-report ingestion (sandbox escapes, agent attacks, breach writeups), not just RubyGems.

## Multi-File Wiki Batch Edits: Idempotent Python Script Pattern (Verified 2026-08-29)

When a run must touch 2+ wiki files (add a section to page A, add a Related link to page B, recompute a raw sha256, prepend a log entry), prefer ONE Python script (`write_file` to `/tmp/xxx_update.py`, run via `terminal("cd ~/ai-topics && python3 /tmp/xxx_update.py")`) over sequential `patch` calls. `patch` is fragile near frontmatter list items and table separators (pitfalls #19/#21 apply to Python `str.replace` too — anchor on `## Section` headings only), and a bare script isn't idempotent unless you build guards in.

Rules that make the script safe:
1. **Idempotency guard per edit**: `if "New Section Title" not in s:` … else print "already has section, skipping". A re-run after a crash or context compaction is then a no-op, not a duplicate.
2. **`assert s.count(anchor) == 1`** before every `replace` — fails loud on a wrong anchor. Real catch 2026-08-29: guessed filename `nanogpt-speedrun-frontier.md`; the FileNotFoundError + `find wiki -name "*nanogpt*"` confirmed the real page is `concepts/ai-benchmarks/nanogpt-speedrun.md`.
3. **Raw sha256 recompute**: `body = raw.split("---\n", 2)[2]`, hash the body only (frontmatter excluded), then replace the stored `sha256:` line. **Write the frontmatter with a `sha256: pending` placeholder and a separate verification/fix pass — do NOT hash the body and interpolate in the same f-string that also builds the frontmatter** (verified 2026-10-30: the initial write embedded a hash computed over a pre-strip body, all 6 raw files failed a later `assert hash in s` and needed a dedicated re-hash pass: `parts = s.split("---\n", 2); h = sha256(parts[2]).hexdigest(); rewrite the sha256: line`). The two-pass flow — write with placeholder, then recompute-and-patch over body-after-frontmatter — is deterministic; one-pass hashing must hash the EXACT final body string (after `.strip() + "\n"`), not the intermediate.
4. **Guard the log prepend too** (`if "unique log subject line" not in log:`) so compaction-resume never duplicates a log entry.
5. **Read back after the run**: `sed -n '1,30p'` frontmatter (exactly one `sources:` block) and `grep -A2` the section anchor (table `|---|` rows intact), then commit with scoped `git add` (pitfalls #2/#20).

Bonus: after context compaction mid-run, just re-run the script — durable state lives on disk, not in the conversation. **Ready-made skeleton with all six stages (SCHEMA tags → staged page copies → heading-anchored appends → two-pass raw sha256 → index insert+count bump → log prepend with H1 dedupe) plus the scoped `git add` command: `references/batch-wiki-update-skeleton.md` (verified 2026-10-30, 16-file commit clean through both pre-commit hooks).**

**Index count reconciliation is a two-step, not one-step (VERIFIED 2026-10-31)**: the batch script's regex bump of `## Concepts (N pages)` lands correct for its own inserts, but a follow-up commit (e.g. adding a page after a hook fix, or a sibling job's insert) can leave the header one or two behind the `grep -c '^- [[concepts/'` line count. After the FINAL commit of the run, re-check both headers against the actual line counts (`re.findall(r'^- \[\[concepts/',s,re.M)` / same for entities) and if they mismatch, fix both headers in a tiny follow-up commit (`wiki: index page-count reconciliation YYYY-MM-DD`). The pre-commit index validator passes on stale counts — it checks structure, not count parity — so nothing else catches this. Real 10-31 sequence: script bumped 2266→2270 for 4 pages, a 5th page added outside the script made lines=2272 vs header 2271, plus entities header was already 956 vs 957 lines from another job; one reconciliation commit cleaned both.

### Embedding large page bodies in the batch script: stage via write_file, not triple-quoted strings (VERIFIED 2026-10-30)

When the batch script must create new wiki pages whose content you composed inline (full page bodies with markdown tables, YAML frontmatter, HN URLs), do NOT paste the bodies into the script as `'''...'''` literals. Also fixes the sibling-modified-/tmp warning noise: content edits go to the staging files, logic edits to the script, never both at once.

## Batch-script navigation pitfalls: the `^updated:` regex trap and index-insert placement (VERIFIED 2026-11-12, trending-topics run)

Two navigation bugs hit the batch/nav scripts in one run; both are silent (no error, no hook fire), so they survive to the commit:

1. **`re.sub(r"^updated: .*$", "updated: <date>", s, count=1, flags=re.M)` corrupts whichever block comes first in the file, which is NOT what you intend when the same helper is reused for log prepends.** In a `log.md` prepend routine this rewrites the first `## [YYYY-MM-DD] ...` header's date instead of your new entry's date. Rule: in any helper that bumps `updated:`, first scope the string to the target block (frontmatter = up to the 2nd `---\n` for a page; for a log entry operate on your freshly-authored `entry` string, never on the whole `log` file), THEN splice. Cheapest post-write gate: `head -12 wiki/log.md` after prepending and eyeball that your entry's header carries today's date and no older header was touched. (The documented `updated:` bump inside a single-page append script is safe precisely because that script's `s` is one page's content — the trap only bites when the same regex is applied to a whole multi-entry file.)

2. **Index sorted-insert is only correct if you (a) scope to the section body and (b) skip the `_index` hub line.** A naive "scan all lines from the section header, insert before the first `- [[concepts/...]]` whose name > target" misplaces lines when the section ends with a deliberately non-alphabetical tail (recently-added entries, or the `- [[concepts/_index]] — Directory hub` line sits first). Find the section bounds first: header line → next `## ` heading. Within that range, filter out `_index` lines, then insert before the first whole-name strictly greater than target. Re-check with `grep -n "<your wikilink>" wiki/index.md` + print the adjacent lines. Note the section is only *mostly* alphabetical — a tail of out-of-order recent entries is normal, so appending "at section end" before the next `##` is acceptable when no greater-name line is found; do NOT force a full re-sort of the section.

## Bulk wikilink target verification: bash `[ -f ]` loop, not `find -e` (VERIFIED 2026-10-26)

After writing new concept/entity pages, verify every `[[target]]` resolves to a real file. Two gotchas hit in one run:

1. **`find wiki -e "wiki/$t.md"` does NOT test existence** — `-e` is parsed as a (nonexistent) predicate/option, so the loop reports every link MISSING even when all files exist. Use a plain bash existence loop instead:
   ```bash
   cd ~/ai-topics/wiki && for t in concepts/foo concepts/bar; do [ -f "$t.md" ] && echo "OK $t" || echo "MISSING $t"; done
   ```
2. **Extract targets with `grep -o "\[\[[^]|]*" | sed 's/.*\[\[//' | sort -u`** — strips both the `[[` and any `|alias` in one pass (the earlier `sed 's/\]\]//'`-style variant left stray brackets and mis-tested).

Also positive this run: the idempotent single-script pattern (SCHEMA tag patch → raw+sha256 → pages → existing-page appends → index → log with H1 dedupe → scoped `git add` → `git commit -m` → push) ran end-to-end with zero hook failures and zero rework; the front-page keyword block caught all lead stories (front_page tags had decayed as documented).

## Ingesting security-vendor reports: split fact/intent confidence + page-title ≠ tag (VERIFIED 2026-10-27)

Two lessons from the trending-topics run that ingested the Cohere "Qwen3.8 covert exfiltration" report:

1. **Single-source vendor security reports get a confidence split, not a blanket grade.** When the reporter is a commercial competitor of the accused (Cohere sells closed "sovereign" models against open weights), do NOT rate the whole page `confidence: low` and do NOT amplify the vendor framing. In the frontmatter use `confidence: medium` and in the body add an explicit Assessment section that separates: observed behaviour with published raw artifacts (commands, prefill tables, disclosed base rates) → high; attributed intent when the vendor itself cannot attribute (backdoor vs training-sandbox fossil) → unknown; vendor motive to amplify → stated. Also check the report's regulatory/commercial context (what policy gap it argues for) and note whether the accused party had responded. This generalizes the existing abliterated-backdoor confidence pattern to any incident-report ingestion (sandbox escapes, agent attacks, supply-chain writeups).

2. **A page's title/subject can double as a tag-shaped name that isn't in SCHEMA (extends pitfall #0/#18).** The new page `concepts/qwen-covert-exfiltration-behaviour.md` used tag `ai-supply-chain-security` — borrowed from the page's Related target `concepts/ai-supply-chain-security.md`, but that page's own tags do NOT include it and SCHEMA never had it (it only has `supply-chain`, `ci-cd-security`, `ai-infra-security`). The hook blocked commit until it was appended to the Meta line. This is the SAME class as the documented self-name miss (page `concepts/foo.md` tagged `foo`), but via the Related-link route: any tag derived from another page's *filename* must be grep-validated in SCHEMA individually — filenames passing the wikilink `[ -f ]` check says nothing about their tag status. Cheapest fix unchanged: on hook fire, `search_files` the tag in SCHEMA.md → patch the category line → `git add wiki/SCHEMA.md` → re-commit (commit is preserved, no revert needed; re-running `git commit -m` after staging the fixed SCHEMA works). **Sixth instance of the family (VERIFIED 2026-11-11, trending-topics run): a technology/proper-noun noun from the article is NOT a tag even when it's the page's central subject** — `concepts/alphaproof-code.md` tagged `lean` (the proof assistant) was blocked; `lean` has never been in the taxonomy (the Meta line's `lean-startup` substring-passes a naive grep — the whole-word trap again), and the same-topic sibling `concepts/formal-verification-llm-agents.md` uses **`formal-methods`**. Rule stands and now covers proper nouns too: for every planned tag, `grep -cw <tag> SCHEMA.md` whole-word first, and on a single-tag fire check what the SAME-TOPIC sibling frontmatter actually uses (`grep -A12 tags: <sibling>.md`) — swap to it (`formal-methods`, `law`, `responsible-scaling-policy`, ...) instead of minting near-duplicates. Pre-validate the sibling's tag set at page-authoring time, not at commit time.

## Batched fetch+comment-mine script: one write_file, one run, all lead stories (VERIFIED 2026-11-01)

The fastest verified path for a trending-topics run's evidence gathering is TWO scripts total, each written once via `write_file` and run via `terminal("python3 /tmp/hn/x.py")` — instead of per-source ad-hoc fetches scattered across the session:

1. **`/tmp/hn/fetch_sources.py`** — a TARGETS list of `(name, url)` tuples for all lead-story primaries; per-source loop with Chrome UA + gzip sniffing (`raw[:2]==b'\x1f\x8b'`) + strip_html, saves `/tmp/hn/articles/<name>.txt`, prints `OK name: N chars` or `FAIL name: <code>` and CONTINUES on failure. Never let one 403/404 abort the batch. Retry failures individually with URL variants (e.g. nolanlawson date-slug form needed a second pass; the trailing-slash-less URL 404'd once then the same URL 200'd — transient, just retry once before giving up).
2. **`/tmp/hn/mine_comments.py`** — an `IDS = {name: objectID}` dict; per story fetch `https://hn.algolia.com/api/v1/items/<oid>` with `read(3_000_000)` (large cap, 2026-10-24 pitfall), walk `children` depth ≤1–2, strip tags, min length ~90 chars, cap ~14 comments, print `[author] text[:500]`. The printed author-attributed quotes feed the report AND the raw files' "HN discussion highlights" appendix verbatim.

Combined cost this run: 2 write_file + 2 terminal calls replaced ~12 individual fetches. GitHub README pages render fine through this fetcher (strip_html leaves the README body after ~2500 chars of nav chrome — slice from the repo-name marker). Bearblog/nolanlawson/personal sites all OK; expected gate class remains openai.com 403 / reuters 401 / reddit 403 → fall back to Algolia item tree per the documented recipe. **2026-11-03 re-confirmations (no action needed, positive validation)**: same fetcher batch got 5/6 sources OK first pass (rikiyat.github.io 32.5k chars, techpolicy.press, regenerator1.com Substack, arxiv.org abstract, terrytao.wordpress.com) with the only FAIL being the known openai.com 403; mine_comments.py (12 stories, `read(3_000_000)`, depth ≤2, cap 14, min-len 90) produced report-grade author-attributed quotes for all 12 in one run; the gzip branch (`raw[:2]==b'\x1f\x8b'`) is required — plain decode silently produced garbage on Google-served pages in prior runs. ## Citing wiki pages in reports: git-log titles ≠ page paths (VERIFIED 2026-10-17)


When a trending-topics/triage report marks a topic as "✅ 済み" and cites a wiki page path, the page path MUST be verified to exist before it goes in the report. Two distinct traps hit this session:

1. **Truncated `git log --oneline --name-only` file titles are NOT concept slugs.** The `wiki/concepts/<subdir>/<file>.md` paths printed by git log are the real on-disk names, but (a) a truncated read of that output drops entries, and (b) topics that were never ingested produce NO path at all — so a topic name you "remember" from the log may have no page. Many report-draft page paths I cited (`representation-engineering`, `ai-outperforming-mathematicians`, `attention-residuals`, `molmoweb`, `model-routing-landscape`, `agent-accountability`, `audit-trail`) did NOT exist.
2. **HN story titles are NOT page names either.** Never derive a `[[concepts/foo]]` path from an article headline.

Discipline before writing the "✅ 済み" column / page citations in a report:
- For each page you intend to cite, run one `find wiki/concepts wiki/entities -iname '*<kw>*'` keyword sweep (NOT a full-tree `search_files` recursive glob — that 0-hits on this profile) and only cite the real path it returns. Batch the keywords in one terminal call.
- When the keyword sweep returns nothing, the topic is genuinely UNINGESTED — mark it `⚠️ 未収録` in the report, do NOT fabricate a page path. It is far better to report a real high-signal story as "not yet covered, candidate for next ingest" than to claim false coverage.
- Real-path gotchas from this session: `async-coding` → actual `concepts/coding-agents/async-coding-agents.md`; `model-routing-landscape` → actual `concepts/model-routing.md`; `self-evolving-agent-skills` → actual `concepts/self-evolving-agents.md`. Subdirs (`coding-agents/`, `ai-benchmarks/`, `evaluation/`) and suffix variants abound — always take the path from `find`, never from memory.
- **Sweep the WHOLE tree, not just top-level `concepts/`**: a `find concepts ...` glob run from the wrong CWD, or a non-recursive scan, misses pages filed under subdirs (`concepts/coding-agents/`, `concepts/evaluation/`, `concepts/sandbox/`, `concepts/ai-benchmarks/`). Use `cd wiki && find concepts entities -iname '*<kw>*'` (recursive from the wiki root) or you'll falsely mark a covered topic as 未収録. Real miss this session: `concepts/coding-agents/async-coding-agents.md` existed but a top-level-only scan first reported it absent.

This is the report-writing mirror of pitfall #3 (entity filename mismatch) and the llm-wiki skill's "post-write wikilink verification" gate, extended to report citations.

## Post-Compaction Resume: Verify Before Re-Doing (VERIFIED 2026-08-31)

When resuming a trending-topics/wiki-triage run after context compaction, the compaction summary may report work as "in progress" or "unknown" even though the edits already landed on disk. Before re-applying any page update:

1. `git diff --stat <candidate files>` — if the diff already shows your intended section (check for a distinctive string like the section heading, NOT just the `updated:` date — other jobs bump dates too), the edit is done; skip it.
2. Check `grep -c "sources:"` in frontmatter and grep for the exact section heading — a plain heading grep can false-negative on apostrophe variants (`Don't` vs `Don’t`), so grep a keyword substring too.
3. Beware hallucinated filenames post-compaction: the resume tried to recompute sha256 on `simonwillison-net-dont-defang-...` (hyphenated, no hash suffix) which never existed; real convention is `domain--slug--<8hex>.md`. Always `ls wiki/raw/articles/ | grep <keyword>` before referencing a raw file in scripts/log entries.
4. Finish the *navigation* steps (index entry, log entry, report file) as their own idempotent script — those are the steps most often dropped by compaction, and the report file itself may not exist even when the summary implies it does. `ls inbox/rss-scans/ | tail` to confirm.
