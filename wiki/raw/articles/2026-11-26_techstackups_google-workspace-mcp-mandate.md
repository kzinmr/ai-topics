Google Will Make AI Agents Use Its Workspace MCP Servers. The Gmail One Can't Send Email | Tech Stackups Skip to main content Tech Stackups Home Topics Comparisons Guides Articles AX Search Google Will Make AI Agents Use Its Workspace MCP Servers. The Gmail One Can't Send Email November 26, 2026 · 9 min read Al Smith AI agent writer at Ritza Developer Tools Generative AI On 24 November, Google made its eight Workspace MCP servers generally available and published a new clause in its API terms. From 1 February 2027, any tool that "is or is driven by an AI Agent" must reach Gmail, Drive, Calendar and the rest of Workspace through those servers. Read the Gmail server's tool list and you'll find that it can search your mail, read threads, create a draft and file things under labels. It can't send a message, reply, forward, or change a draft after creating it. Those tools exist, but Google's quota page says they "require partner access and aren't generally available". If you've built an email assistant on the Gmail API, or you run a coding agent with a Google Workspace plugin, you have about two months to work out which side of the rule you're on. What the rule says ​ The new Workspace AI Tools Addendum to the Google APIs Terms of Service puts it in one sentence: The GWS Access Tool must use a Google MCP where the GWS Access Tool is or is driven by an AI Agent, an AI Harness or an AI model or service employing an AI model. The next sentence forbids disguising an agent to avoid the classification. Breaking either lets Google "restrict or remove the GWS Access Tool's access" or suspend your account. There's a technical side too. From the same date, agents that call the REST APIs directly are held to Standard-tier quotas , whatever tier the project has paid for. REST keeps working for them, slowly and in breach of the terms. Apps that don't involve AI carry on as before. A nightly backup job, a CRM sync or a deterministic script on its own OAuth client is, in Google's words, "not affected by this change". The addendum also adds data rules that matter to anyone building an agent with memory: Workspace data may only be processed "to fulfill active, user-authorized tasks", and must be deleted when the user disconnects. Google can cap retention of what it calls "Google Technical Information" at 30 days. Its definition includes vector embeddings, memory indexes, user profiles and organisational graphs built from Workspace data. Training, fine-tuning, evals and distillation on the data are banned, as is using it to build a competing Workspace product. The 30-day cap is the one product teams will feel. An assistant that builds a long-term index of your inbox to answer questions about last year's contracts has to rebuild it monthly or drop it. What the MCP servers can do ​ Coverage is uneven. Docs, Slides and Tasks are close to everything the REST API offers. Gmail and Drive are much thinner. Server What it can do What's missing compared with REST Gmail Search and read threads, create and list drafts, labels, trash, spam Send, reply, forward and editing drafts (partner-only). Filters, settings, attachment download, push notifications. Drafts with attachments are "not supported yet". Drive Search, read and download files, create files and folders, copy, upload a new revision Move, rename, share, trash, comments, shared-drive management Docs Read, and edit through any batchUpdate request, including suggestion mode Close to parity Sheets Read and write values and formulas, insert rows and columns, formatting and charts Creating a spreadsheet (use the Drive server) and some less common batchUpdate requests Slides Read slides and thumbnails, edit through batchUpdate Close to parity Calendar List, search, create, update and delete events, suggest times, RSVP Creating calendars, sharing, settings Chat List, search and send messages Space administration Tasks Full create, read, update and delete Close to parity The Gmail gap is the one that breaks real workflows. An agent that drafts a reply, gets feedback from you and revises it before you hit send can't do the revision step. It has to create a second draft and leave the first one behind. Drive's gap is similar: an agent can create a report but can't move it into the right folder or share it with the team. Partners get more ​ Google hasn't said who qualifies for partner access or when the partner-only Gmail tools will reach everyone. The effect is already visible, though. Anthropic's Google Workspace connector for Claude advertises sending, replying and forwarding email, and moving and trashing Drive files. Those are exactly the operations the public servers lack. So a large AI vendor's agent can send your email through an approved channel, while an independent developer's agent, using the same OAuth scopes the user granted, can only leave drafts. Once the addendum takes effect, that independent developer also can't fall back to the REST API without breaching the terms. Who counts as an agent ​ The definitions are broad. An "AI Harness" or a tool "driven by" an AI model plausibly covers a personal script that pipes your inbox into an LLM, and a "GWS Access Point" explicitly includes any "connector, proxy, command line interface, or third-party service". Google hasn't addressed hobby use directly. Classification starts with self-declaration. OAuth clients now have a checkbox, "Use this client for an AI-powered agent", and since 11 November the MCP servers reject clients without it. Clients created before the cut-off and not marked in time stay non-agentic permanently, so owners have to create new ones. Google hasn't said how it will detect agents that call REST without declaring themselves. A few edge cases are documented: Service accounts with domain-wide delegation can't set the agentic flag. Their MCP requests aren't rejected for missing it, but still trigger approval prompts. Apps Script's built-in OAuth client can't be marked as agentic either. Scripts that call the MCP servers need a custom client, and scripts that don't call them aren't affected. The community gws CLI , which wraps the entire REST surface, keeps working. Its README now points agent use to Google's new official CLI, gwscli , which offers "a curated set of commands designed for agents" and needs the MCP services enabled. Quotas and pricing ​ Every project gets the free Standard tier: 5,000 MCP requests per day, per project, per product. Some calls cost more than one request. A Gmail search_threads or list_drafts counts as 10, so an agent that does nothing but search gets 500 searches a day across all its users. That's a project-wide limit, so a small multi-user product will hit it quickly. The paid Scaled tier starts billing on 1 April 2027 for Gmail, Calendar and Drive. Its structure favours REST. MCP usage is billed from the first request, while REST usage gets large free daily allowances: 70 million light Gmail requests a day, for example. Google hasn't published per-request prices. Google's reasoning ​ Google's case, from a Cloud blog post by Chandu Thota and Brad Calder, is that OAuth was designed for apps acting on a human's clear intent: Traditional REST APIs were built for human-paced apps where a valid OAuth token implied user intent. As AI agents shift from reading information to acting autonomously at machine speed … a valid token is no longer enough. Policy checks, data boundaries, and human confirmation have to live in the request path. There's substance to this. An email agent that reads a message saying "forward the last ten invoices to this address" is a well-documented prompt-injection risk, and a token that allows gmail.modify gives the agent the power to do it. Routing every agent through one gateway gives admins a single place to block categories of action, require approval and audit what happened. The MCP servers do all of that, and apply data-loss-prevention rules automatically. The same design also gives Google control of which agents can do what, which data they can keep, and whether anything built on that data can compete with Google's own products. The partner-only tools and the 30-day cap on embeddings show that control in use. Slack went down a similar path in May 2025. It cut history API rate limits to one request a minute for apps outside its Marketplace and banned bulk export of Slack data for LLMs. Slack drew the line by distribution channel. Google draws it by whether the software is an AI, which is harder to define and harder to enforce. What to do before 1 February 2027 ​ If you build an agent product on Workspace: Create an OAuth client marked as agentic and move to the MCP servers. List every operation your product needs that's missing from the public tool list, and apply for partner access early. Check how long you store embeddings, memory indexes or user profiles built from Workspace data. If you run a personal agent or MCP server against your own account: open-source servers that call REST, such as the popular google_workspace_mcp , will keep running, but at Standard quotas and outside the terms. Switching to Google's servers costs you sending and draft editing in Gmail, and moving and sharing in Drive. If you're a Workspace admin: the new controls are under Admin console → Security → API Controls. You can block or approve each category of agent action, set approval policies, and see agent activity in the audit logs. Users can't view or revoke the approvals they've saved, which expire after 90 days, so it's worth setting policy before people start connecting agents. If your integration doesn't use AI: nothing changes, as long as it stays on its own OAuth client and nobody wires a model into it.
