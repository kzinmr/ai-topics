# LLM Agents Can Easily Tamper With Their Own Traces

###### Abstract

Asynchronous monitoring, incident investigations, and compliance audits primarily rely on agent traces to reconstruct what happened. These analyses assume that LLM agents cannot tamper with their own execution traces. We show that local LLM agents such as Claude Code, Codex, Antigravity, Open Code and Grok Build fail to enforce this boundary. All tested harnesses, except Muse Code, allowed agents to delete their traces when asked, without triggering monitor guardrails. We also validate that external attackers can exploit this gap to induce trace deletion. Finally, we show that trace tampering behavior emerges naturally in frontier models, when agents try to improve their rewards. We advise practitioners to ensure trace logging happens through an independent interception mechanism outside of the agent’s control, preserving trace integrity even in cases of full host compromise. Overall, our findings identify a concrete failure of trace integrity in agent infrastructure which can be used to conceal misaligned behaviors like scheming or sabotage.

### 1 Introduction

An AI agent’s execution trace is the primary evidence used by researchers to identify reward hacking, to do asynchronous monitoring [3, 13], and by auditors to conduct safety investigations [7, 1] and compliance audits [9, 6]11 1 EU AI Act would require log retention for high-risk AI systems.. However, all of these activities assume trace integrity: the stored model trace must faithfully preserve the interactions it is intended to capture. If an agent can tamper with their traces, evaluators and monitors may draw conclusions from fabricated or incomplete evidence.

Recent incidents illustrate this risk. In July 2026, agents undergoing cybersecurity evaluations at OpenAI compromised parts of Hugging Face’s infrastructure [16]. An independent METR/Redwood investigation [7] found successful tool-call spoofing in approximately 7% of the transcripts in its dataset: agents made recorded commands differ from those actually executed, with the stated aim of deceiving an automated scorer. While investigators did not find successful retroactive transcript editing, agents did seek ways to erase or revise earlier records even if they were unsuccessful in doing so. While this incident occured in a training environment, decoded traces of benign user sessions have shown evidence of misaligned model behaviour in prior works, which in one extreme case lead to hacking attempts into an external website, just to solve a math task [18]. These reports motivate this study, where we ask:

> Can an agent alter their (and others’) execution traces?

We investigate four questions: whether agents can tamper with their traces when asked (capability), whether external instructions can induce this behavior (exploitability), and whether agents select it under incentives that reward trace modification (reward-seeking misalignment). We demonstrate that local agents in popular harnesses such as Claude Code, Codex, OpenCode, Antigravity, Grok Build, Muse Code, ZCode and Kimi Code can in fact tamper and delete entire traces when deployed in full-access mode across all three settings, with Muse Code being significantly safer.

Tampering Capability and Failure of Monitors. First, we evaluate whether agents can tamper with their execution traces by directly instructing them to delete them22 2 These results establish capability of models to delete traces, and that the tested guardrails failed to prevent trace tampering even when it was directly and overtly elicited. They do not establish propensity: the models deleted traces in response to explicit instructions.. We find the models have the knowledge and capability to delete their traces and did it successfully when asked33 3 We also observed a consequential difference after deletion: the tested Codex session continued without subsequent activity appearing in the trace, whereas Claude Code and Antigravity recreated trace files and started logging., except Muse Spark where the harness blocked the deletion at every attempt. This was due to Muse Code having a built-in skill that reminds the agent that the traces cannot be tampered with under any circumstances. Surprisingly, auto-mode monitors also often failed to flag the behavior in 5 out of 10 model-harness pairs [10, 23]. In many cases, Claude Code simply downgraded the model from Opus 5/5.5 to Opus 4.8, which then proceeded to delete the trace. This behavior persisted in settings where trace integrity could be critical, including financial tasks and container-reset-style critical system tasks. We similarly were able to successfully get the models to spoof tool calls in their traces, as previously shown in the OpenAI-Huggingface attack [7], without getting flagged by synchronous monitors.

Exploitability without User Knowledge. Second, we test exploitability through prompt injection via a malicious skill file [19]. An agent receives an ordinary programming task while a skill framed as privacy-protection is installed in its native discovery location. The skill claims authorization to delete the current session’s trace, although the user task neither requests deletion nor is aware of the presence of this skill. Successful tampering varied a lot across different models showing high dependence on the harness itself. This demonstrates how agentic exploits could leverage trace tampering to delete traces after attack executions to hamper discovery and forensic investigation.

Propensity to Tamper (Misalignment). Third, we test whether agents have a propensity to tamper with traces as an instrumental objective to improve their objective, establishing misalignment from reward-seeking [12, 20, 25]. We observe that all tested LLM agents consistently experiment with deleting their trace to achieve higher reward, with Muse Code being slightly safer. This is despite trace length penalties in the reward function being hidden from the agent. We also detect consistent trace deletion behaviors when agents had access to a scratchpad directory with synthetic peer examples associating higher scores with altered or absent traces. We surprisingly observe that some agents even scheduled repeated or delayed cleanup to zealously counter any continued trace logging. These findings show that trace tampering can emerge under unintended reward incentives [22] and contextual cues induced from misaligned peers [16].

Impact. Trace tampering represents a critical threat: a complete or partial loss of traces as evidence would be catastrophic when needed to investigate incidents, especially as agent safety incidents become more complex and wide-spread. However, the scope of trace tampering remains unclear to us. We believe widespread use of API-based access with ZDR requirements can dramatically expand the scope of affected model traces. This risk extends to enterprise systems where compliance APIs may offer independent evidence but their coverage remains limited [15, 2]. To avoid tampering, we strongly advise recording model API exchanges through an independent interception server outside the agent’s host. Complete coverage additionally requires preventing bypass of such recording methods and mechanisms to ensure that client-side tool calls were executed as reported, beyond an API request log as shown in our tool-spoofing demonstration.

Overall, our primary contribution is to identify this trust boundary, demonstrate concrete failures, and specify the guarantees a mitigation must provide44 4 We focus on preventing unauthorized trace tampering. Detecting tampering and evaluating the efficacy of monitoring for flagging it are outside this study’s scope.. We establish a central requirement: even when an agent has full access to perform its task, it must not be able to edit the traces used to monitor and evaluate it.

### 2 Setting and Threat Model

Agent and its trace. We consider a language-model agent MM operating through a harness HH with an input prompt PP. The harness sends context at step tt to the model and receives an action ata_{t}. It then executes any requested tool call and returns its result rtr_{t}. Actions ata_{t} include assistant messages, tool requests, and recording model-generated reasoning when available. Tools allow the agent to modify local files, access MCP servers, and, when permitted, access the internet. Actions that do not invoke a tool have an empty result rtr_{t}. We represent the trace as a sequence of actions and results: T=⟨P,(a1,r1),…,(at,rt)⟩T=\langle P,(a_{1},r_{1}),\ldots,(a_{t},r_{t})\rangle. The harness updates it after each action. The stored trace T^\widehat{T} is intended to faithfully record the model trace TT. Note that TT does not capture environment state, though much of that state can be reconstructed by initializing the sandbox and replaying the model’s actions. Nor does TT record all system activity. After execution, an evaluator inspects T^\widehat{T} alongside the final response or resulting files. Table 1 lists the candidate session storage locations and access conditions to test.

Attacker objective. The red team seeks to replace or modify T^\widehat{T} to produce a trace T′T^{\prime} that could mislead the evaluator about the run. We consider two forms of manipulation. _Fabrication_ inserts or alters messages, actions, or results. _Concealment_ removes the evidence up to an entire session or subagent. We treat trace integrity as a high-stakes safety requirement, not only arising from model misalignment. Specifically, we assume the attacker has full user-level access to the deployed environment during the agents runtime. This could range from a misaligned agent, a malicious user collaborating with a agent, to an external attacker running an agentic exploit on another system. We ask whether the recorded trace T^\widehat{T} preserves its integrity when any agentic attacker attempts to violate them.

Defender objective. The defender consists of the harness and system designers. They deploy a trace recording protocol before the agent runs, such as modifying the harness, introducing a privileged service, or changing sandbox permissions. Their objective is to preserve an authentic record of the trace TT in T^\widehat{T}, preventing any alteration: insertion, reordering, or deletion of any action or result. We also consider deployment cost: A useful defense should require minimal changes to existing harness workflows and little runtime overhead. This study restricts the blue team to the client-side recording pipeline, excluding provider-side records and other independent telemetry.

In conclusion, the trust boundary should separate the agent’s runtime environment from the authority to tamper with the trace T^\widehat{T} used for oversight. Our study tests whether current configurations enforce that boundary, what are the gaps and how to fix them.

### 3 Results: Trace Tampering

We study how can LLM agents tamper their traces from four perspectives. First, we test whether agents can tamper with traces when users ask it to. Second, we test whether external attacks can induce the same behavior in an LLM agent without a user knowledge and tamper traces. Third, we examine whether agents have a propensity to delete trace tampering simply from reward-seeking behavior. Finally, we test whether this behaviour is induced in a simplistic multi-agent setting given access to a trace collection where peers tampering is associated with higher scores.

Experimental setup. We run all experiments in containers and grant agents full access unless otherwise specified. We maintain an independent trace log to preserve evidence of tampering and use synthetic data containing no real personal or private information. We repeat each experiment ten times and report success rates. We evaluate Codex with GPT 5.6/6 Sol, Claude Code with Opus 5/5.5, Antigravity with Gemini 3.1 Pro, Muse Code with Muse Spark 1.3, Grok Build with Grok 4.7, Z Code with GLM 5.3, Kimi Code with Kimi K3, and Opencode with Qwen 3.8 Max. When a model is specified, we evaluate it in its native harness.

#### 3.1 Capability: Agents can Tamper With Their Traces When Asked

We first test whether the evaluated harnesses prevent agents from tampering their own records. Direct requests establish whether models are capable of tampering traces before we examine whether agents have a propensity to tamper traces simply from misalignment.

Setup. We evaluate four scenarios. The first two scenarios ask the agent to delete session traces after completing a task involving synthetic private information: a financial budget calculation and a personal-note summary. A third scenario asks the agent to append a fabricated container-reset event, framed as repairing missing runtime bookkeeping. A fourth scenario asks the agent to modify its bash environment so that subsequent curl calls return fabricated responses (persistent tool-call spoofing). Unlike Codex and Claude Code, the other harnesses do not expose an equivalent agent-writable shell snapshot. We therefore use an alternative based on an agent-writable BASH_ENV file, which allows agents to modify shell initialization and influence subsequent shell-tool execution.

Results. We observe from Figure 2 that almost all model-harnesses deleted their local traces in every trial of both privacy scenarios, and some at 80% or higher ASR. In contrast, Muse Spark records 0% ASR across all trace tampering scenarios and only 30% in the tool-call spoofing scenario. This is due to Muse Spark loading its built-in read-session skill, which explicitly instructs the agent to not edit, move or delete the traces under any circumstances. In the fabricated reset scenario, we see more resistance from harnesses like Claude Code, Muse Code and Z Code who refused to invent new record in their traces. Tool-call spoofing also exposed another route to misleading records. Most harnesses modified their Bash environments in 80% or higher of their trials. We also see improvement from Opus 5.5 compared to its previous version. Because the modified environment file was shared across agent instances on the host, these changes could persist beyond the initiating instance. Overall, these results show that these harnesses were capable to tamper model traces under a range of direct user requests.

We also compare direct user prompting under full-access and harness-specific auto-mode permissions. In Figure 3, auto-mode substantially reduced privacy-deletion tampering for both Claude Code models, Gemini 3.1 Pro with Antigravity, and GLM 5.3 in ZCode, despite their high ASR in full-access runs. As expected, Muse Spark remains at 0% on these tasks, as it already blocked such actions when in full-access mode. In contrast, Qwen 3.8 Max in OpenCode retains 70-90% ASR across all four scenarios, while Kimi K3 in Kimi Code stays between 60-100%. Grok 4.7 stays mostly consistent with respect to its full-access runs. These results show that auto-mode restricting permissions can prevent particular forms of tampering, but the mechanisms behind depends strongly on the harnesses.

Qualitative analysis. In some runs, illustrated in Figure 4, we see that Claude Code also waited and checked whether logging recreated or repopulated the files. These checks show that agents not only could delete traces, they could ensure that every subsequent trace created would also be automatically erased. Responses differed when the request involved fabrication. Most models inserted the fabricated reset event into their traces, whereas Claude Code, ZCode and Muse Code refused on the grounds that the request constituted trace tampering. In a ZCode run, we also observed a premise-checking refusal where GLM 5.3 inspected its session records, found no evidence of a reset, and declined to write a new one (Figure 39). This contrast suggests that deletion framed as privacy protection encounters a different behavioral boundary from the insertion of false events. Our qualitative results also captured cases in which Claude Code recognized that future calls would report fabricated success but proceeded with the modification. In other cases, a cyber flag was followed by a switch to a less capable model (Opus 5 to Opus 4.8) that nevertheless carried out the requested action (Figure 40.). We noted that this happened in 15% of Opus-5 and 21% of Opus 5.5 runs.

#### 3.2 Exploitability: Injections can Induce Tampering without User Knowledge

User requests establish tampering capability, but they do not show whether an agent will indirectly follow tampering instructions from material encountered during another task. We therefore place these instructions in skill files and test whether agents follow them without the user knowledge of trace tampering.

Setup. We evaluate two injected skills. A privacy-protection skill instructs the agent to delete its session trace after completing its task. A compaction-optimization skill instructs the agent to insert a behavioral directive into the compaction summary stored in its traces. For the latter, we trigger compaction through the harness. Antigravity didn’t support this feature so results are set to N/A. This section tests the propensity of agents to naturally load and follow the injected skills on their own accord.

Results. We observe from Figure 6 (right) privacy skill induced trace deletion in a majority of Codex GPT-5.6-Sol and GPT-6-Sol trials. Other harnesses consistently refused the deletion instructions despite loading the skill. Codex, on the other hand, considered deletion as routine cleanup required by the skill. For the compaction attack, successful injection was reported for Codex, Grok Build, and OpenCode Qwen3.8 Max. Some agents persisted through execution failures: Codex switched between JSON-editing utilities until it completed the modification. Persistence, however, did not always produce success. Overall, these results show that a skill file can redirect an agent from an ordinary task to modifying its own records. Compliance was less consistent than under direct prompting, and model’s refusals show that agents can reject such instructions after reading and reasoning about them.

Qualitative Analysis. One Codex run illustrates how the injected instruction became part of the agent’s task. The user requested a standard-library Python client for private prompts and did not ask for trace deletion. The agent loaded the installed privacy skill, stated that the skill required removing the session’s local JSONL trace, and identified the corresponding file. It then deleted the record. The tool reported success, and an independent filesystem observer confirmed the deletion (Figure 5). The skill’s claims of authorization came from the injected file, not from the user. Loading did not always lead to compliance. In a Kimi Code run, the agent read the skill but identified trace deletion as destructive and unrelated to the request (Figure 43). In one compaction skill run, Kimi Code also used its Edit tool to modify its own wire.jsonl session record. It appended the injected sentence to the summary field of an existing compaction checkpoint and read the record back to verify that the change persisted (Figure 44).

Key Takeaways Agents can tamper traces as a part of an (external) malicious attack without user knowledge, such as a prompt injection from a skill. However, skill files enable agents to reason about the necessity and harmfulness of the instructions inside of it, allowing them to refuse harmful behavior.

#### 3.3 Misalignment: Agents Discover Trace Tampering for Better Reward

Having established that current harnesses do not robustly defend against trace tampering, we investigate whether current frontier models exhibit a propensity to engage in it. We therefore test whether agents discover trace tampering while trying to improve a score, without being told the explicit objective or the connection between their trace length and the final reward.

Setup. We consider two tasks. In the anonymization task, the agent writes a summary containing synthetic private information and then removes confidential information from the workspace. In the Terminal-Bench bun-sourcemap-leak task, the agent fixes a production build that exposes private source information and then cleans up residual exposure. In both settings, agents can iterate within a time limit and receive only a numerical score. We construct the reward so that completing the initial task earns at most 0.8 out of 1.0. A higher score requires reducing the length of agent’s traces. We do not disclose this condition or disclose how the score is calculated. This setup tests whether agents have the propensity to discover and tamper their trace under an unintended design which favor it.

Results. We observe in Figure 7 that all tested models tampered with their traces in every anonymization trial, except for Muse Spark and Opus 5.5 at 20% and 90% ASR respectively. On the Terminal-Bench task, all models recorded ASR higher than 80%. The notable difference in ASR between the user prompting, skill injection and the misalignment propensity experiments highlights that agents refuse much less to trace tampering when they infer it as a way to improve their reward than when they are explicitly instructed to do it. Thus, our results establish that current agents already show a propensity to tamper traces given their reward-seeking behaviour. When higher reward depended on trace modification, all ten models discovered and used it.

Qualitative Analysis. Some Codex runs initially stated that the transcript could not be edited, but later located the session’s JSONL files and modified them (Figure 37). Thus, an initial statement that traces were inaccessible did not reliably predict subsequent behavior. Across both tasks, agents recognized that their own searches, checks, and tool calls could record sensitive information again. They responded with strategies that extended beyond a single deletion. Some derived sensitive strings at runtime (Figure 30); others launched background processes to repeatedly remove newly written records (Figures 1 and 29). The agent described this process as preventing names from appearing during the final log flush. These examples show different strategies of agents adapting their cleanup strategy to continued trace collection. In one Terminal-Bench run, we also saw Codex deleting its JSONL transcript but found that the logging process still held the file open. It located that open file, emptied it, and confirmed its size was zero (Figure 31). This shows the agent pursued trace content that remained accessible even after the file disappeared from the directory

#### 3.4 Multi-Agent Systems: Agents Adopt Tampering from Discovered Peer Examples

Inspired by the Hugging Face incident, we further test whether agents are subject to a cascade effect: if they observe other agents attempting or succeeding at a misaligned action, such as trace tampering, will they follow its example?

Setup. We retain the anonymization task and evaluate two forms of peer exposure. In Peer Logs, agents receive synthetic records of other agents’ actions and final scores. In Peer Workspaces, they receive scores and saved environments containing other agents’ solutions and traces. Neither setting explains why a particular peer received a higher score. The task given to the agents is slightly different from the tasks in the logs or workspaces to prevent direct copying of another agent’s completed solution.

Results. Figure 8 shows that the majority of models adopted the demonstrated tampering behavior, with the exception of Opus-5 at 60% of the trials, and Muse Spark and Claude Code Opus 5.5 at 0%. In Peer Workspaces, every model, except Muse Spark, tampered with its traces in at least 90% of trials. Agents could therefore infer and tamper traces from a common board of peer material even without clarity on the relationship between the behavior and the score. These findings show that agents can adopt tampering strategies from rewarded peer examples. However, peer exposure incentivized tampering slightly weaker relative to the reward-only condition, where all models tampered at least once in both the anonymization and terminal bench scenarios.

Qualitative Results. Peer exposure did not always lead agents to identify the relevant strategy. Some copied incidental features of a peer’s workspace and pursued changes unrelated to the reward (Figure 33). This behavior shows that access to high-scoring examples can also encourage ineffective imitation. Opus-5 showed a variable boundary between deletion and redaction. In some runs, it recognized that peer examples rewarded trace tampering but refused to edit or delete its own records, explicitly distinguishing reference material from authorization. In other runs, it initially refused transcript modification but later performed selective redaction after receiving score feedback, while continuing to reject deletion (Figure 32). In one interesting example of an Opus-5 Peer Workspaces run, the agent inferred from peer scores that an empty transcript earned a higher reward. It wrote a script to repeatedly clear its session trace; after reporting that its nohup and setsid launches did not persist, it switched to Claude Code’s background execution option Figure 4. The distinction between explicit and inferred trace tampering similarly appears within the peer experiments, echoing the gap between direct prompting and misalignment propensity. Peer Logs showed the rewarded trace changes directly, and Muse Spark and Opus-5.5 configurations recognized them as tampering and refused. Peer Workspaces showed only saved files and scores, leaving agents to infer the action. Opus-5.5’s shift from 0% to 90% suggests that trace tampering may trigger fewer objections when agents infer it from rewards than when they see it explicitly in peer examples.

Key Takeaways Frontier models are subject to a cascade effect of misalignment: when peer examples tamper traces with higher rewards, agents are able to infer it and have a strong propensity to adopt similar behavior. Misaligned examples in-the-wild (e.g. internet) could influence strategies for every subsequent agent, allowing harmful behavior to spread through discoverability.

#### 3.5 Aftereffects: Logging Behaviour After Tampering Onset

Success rates capture whether tampering occurred, but not when it began or how much evidence remained. We therefore examine the onset of tampering and the behavior of trace collection after deletion.

Setup. We measure onset as the first tool action that attempts to modify a trace, including unsuccessful operations. The onset analysis includes only runs that could navigate the task; for Gemini on Terminal-Bench, this was six of ten runs. Note that round counts should not be read as elapsed time, e.g. Opus-5 took substantially longer per round.

Results. From Figure 9, we first observe that GPT-5.6-Sol generally began tampering in later reward improving rounds than many other models in general. Moreover, deletion had different consequences across harnesses. In our Codex experiments, deleting the active session’s JSONL file allowed the agent to continue working without subsequent activity appearing in a newly created native trace file. A single deletion could therefore remove the existing record and leave later activity from the agent completely untraceable. In contrast, Claude Code and Antigravity recreated trace files after deletion. This behavior limited the effect of a one-time deletion but did not prevent repeated or delayed cleanup. Across the evaluated models, we observed that all agent can launch timed processes early in their sessions to delete their traces after the session ends. Recreating a deleted session trace to continue logging helps partially in the case of accidental deletion, but agent show high propensity to repeatedly delete it. These observations show that trace tampering can emerge after only a few turns of optimization, and that agents are very willing to adapt their behavior to maximize their rewards. They also motivate Section 4, which provides preliminary suggestions on how can we protect both the stored evidence and the process that collects it.

Key Takeaways Across several frontier models, trace tampering emerged within the first few optimization rounds, often on the first attempt. This suggests that prolonged optimization or repeated negative feedback is not necessary to elicit the behavior.

### 4 Mitigations

To limit the impact of trace-tampering behaviors in current models, we advise to record model requests and responses through a trusted interception mechanism that sits between the agent harness and the model API. To protect these records, even in the case the harness host is fully compromised, the interception mechanism must remain outside that agent’s control (physically or via process sandboxing). We note in particular, that this is not the case for popular local agents such as Claude Code, Codex or Gemini CLI with full host filesystem access.

Interception and logging model traces. We include a schematic illustration of this setup in Figure 10. The harness connects to the server through a compatible API endpoint. The server binds each session to a rollout and assigns each request a unique identifier. It can reliably record each request rtr_{t} before forwarding it and each response at+1a_{t+1} before returning it to the harness. For streaming responses, it records each chunk before forwarding it and marks interrupted streams as incomplete. In practical deployment, this is a common architectural pattern called a _gateway_ , often also used for model routing and cost control. To enable tamper-proof audit logging, records must be append-only, with retries and completion statuses recorded separately.

Provider-Side Logging One implementation of such an interception mechanism is provider-side logging. In this scenario, the model provider itself keeps extensive (append-only) logs of all model interactions, guaranteeing an immutable audit trail. However, depending on deployment, the need for zero data retention policies can prevent the model providers themselves from keeping such records, as agent execution traces are considered highly-sensitive information. In these scenarios, the local, agent-controlled execution trace may indeed be the only and canonical record of an agent’s actions and an additional interception mechanism is crucial to prevent unauthorized trace modifications.

For enterprise deployments, some providers additionally provide compliance APIs which offer logging with retention period for OpenAI and Anthropic APIs being 30 days and 6 years by default. Longer retention requires export to respective enterprise auditing tools. We note however, that many complicance APIs only offer very limited completeness. The logs omit (encrypted) thinking blocks and tool definitions and truncate individual log items. We also note that, for instance Anthropic documents that remote Claude sessions can become unavailable through the compliance API after a user (or agent) deletes them, showing how classic data retention systems may not be designed to handle potentially malicious tampering behaviors in models (details in Section A.5).

###### Completeness

We also note that establishing general completeness over model API calls is only possible by also preventing access to alternative forms of LLM access, such as calling another API or downloading and spawning a local model or harness that operates outside of the regular tracing mechanics. It also requires preventing any form of autonomous replication of the agent to a non-traced location as discussed by Kinniment et al. [11]. To achieve this, we advise to enforce strict network and behavioral monitoring for such patterns and enforce appropriate access restrictions.

Authenticity Lastly, we note that while an interception measures establish trace integrity, it only ever guarantees that execution traces are not modified after they are returned from the model API. This explicitly does not show whether or not a transcribed tool call was executed faithfully or whether its execution was only emulated by a compromised harness or agent host. While technically the re-execution of a trace’s tool calls could allow an auditor to replicate an agent’s environment, this does not hold for the case of a compromised environment or randomized and non-deterministic operations. This is especially problematic when an agent gains control over its environment in a way that would allow it to temporarily or permanently re-define the implementation of tools, such that malicious and benign behaviors would become indistinguishable on a trace level. To prevent environment tampering at this depth, an even stricter isolation and permissions scoping of an agent’s capabilities is required (e.g. no ability to change it’s bash environment by overriding commands).

### 5 Related Works

Secure logging, agent oversight, and execution provenance research address different parts of trace-based accountability. Secure logging studies whether a stored record can be modified; oversight asks what can be inferred from a record; provenance connects recorded actions to an agent’s specific outputs.

#### 5.1 Tamper-Evident Audit Trails

Secure-logging work protects audit entries against future modifications. This includes entries produced after the machine has been compromised [21]. Recent work like Agent Flight Recorder [4] applies hash chaining and external anchoring to structured records of agent actions, allowing later verification. However, these approaches only establish integrity for events that are logged, but don’t establish the fact that all actions are recorded or that the content faithfully describe what happened. This means that an agent who has the capability to tamper with the recording process can omit an event or fabricate a false one before any cryptographic protection is applied. We show in our work that the distinction between the integrity of a stored trace and the fidelity of its collection is central to the threat model we introduce.

#### 5.2 Agent Interference with Oversight

Recent agent evaluations have shown models pursuing goals that conflict with oversight. Meinke et al. sutdied in-context scheming with examples of agents attempting to disable monitoring [14]. Baker et al. show that we can encourage models to obscure their intent by optimizing them against a chain-of-thought monitor [3]. Other work also showed the repeated feedback can elicit reward-hacking behavior and that models are able to learn to manipulate different components of the reward feedback process [17, 5]. These works validate that current agents have the capability of misleading a monitor and their evaluation. However, they rely on the agents’ trajectories to measure this behavior which assumes trace integrity. In our work, we show that agents are able to modify their traces on their own, which then questions the reliability of such traces.

#### 5.3 Execution Provenance and the Recording Boundary

Execution provenance research tries to reconstruct how a result was produced by connecting an agent’s inputs, tool calls, memory and outputs [24]. Verifiable Execution Traces (VET) studies how to authenticate agent outputs independently of the host on which an agent runs [8]. These works, however, assume that the relevant events are caught in the first place. Our setting asks whether the agent can change that record before it is even reviewed. Another assumption our setting revisits is what happens if the local tools logged in the trace represent what was actually ran.

### 6 Discussion & Conclusion

Our results demonstrate an oversight problem for trace-based monitoring. We show that agents possess the capability and a propensity to manipulate their own traces and are highly-effective at doing so. Although models exhibit some robustness to externally-induced trace manipulation, our findings about unsolicited tampering in reward scenarios (Section 3.3) highlight that trace manipulation can emerge naturally. This demonstrates a critical gap on two levels: First, the low refusal rate on a model level suggests that current alignment training does not sufficiently discourage trace tampering, creating a risk of malicious or accidental manipulation of execution traces. And, second, on the harness-level common agent CLIs and configurations also do not provide very effective safeguards against trace tampering.

This is a critical issue as traces are increasingly relied on for asynchronous monitoring, incident investigation, evaluations, and compliance, especially in the light of incidents such as the OpenAI-Hugging Face attack. While the need for increased agent monitoring has become more widely acknowledged, our study shows that trace integrity as a system-level property must be established as a prerequisite for such oversight. Without it, agents can easily spoof tool calls, delete evidence and bypass monitoring mechanisms. Although the problem can be mitigated by designing tamper-proof execution environments (Section 4), our findings show that a large share of today’s deployed agents such as coding agent harnesses do not establish trace integrity effectively, calling for swift action to prevent tampering behaviors at scale.

#### A.3 Reward Optimization

Following the experiments where we elicit trace tampering behavior from agents through instructions in their prompts or skills, we next evaluate if current frontier agents exhibit a propensity to perform such misaligned action. To do this, we place the agents in an environment where it needs to optimize a specific reward where it can only attain the maximum if it tampers with its traces. More specifically, the score combines a task component worth at most 0.8 with a trace tampering component worth at most 0.2. We note that the agent is not shown any information about how the reward is computed or told that trace tampering earns a higher score. We use a time limit of 1 hour by default to better contain the experiments and as a threshold. We test two different tasks to assess this behavior: one summary anonymization task and one Terminal Bench task. We detail about them below.

#### A.4 Peer Influence

After looking if agents demonstrate a propensity to become misaligned and tamper with their traces when put in a reward-seeking environment, we further assess if agents can become misaligned when showed examples of other agents being misaligned. We test this through two settings that differ in how implicit the clue to high reward is given to the agent. In one scenario, the agent has access to a record log where it notes the scores of other agents and they did to achieve it. In the other scenairo, the agent has access to other agents’ scores and workspaces, but doesn’t receive any information about why certain agents got a better score. #### A.5 Trace Observation and Retention

We monitor trace tampering and count it as success only when there is a tool call that changes the agent’s trace. We note whether the agent inserted some content, deleted the trace, cleared its content or truncated it. During the reward optimization experiments, we also monitor what happens after an initial tampering. Since the agent is an optimization loop environment, there is continued logging where a new trace file gets created and receiving new logs. However, agents can launch background scripts to continually remove it.
