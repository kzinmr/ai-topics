# Polymorphic Inference & Together Compiler (TKCC)

**Polymorphic Inference** (Together AI, November 2026) is a research framing for inference in "many shapes": serving systems that continuously adapt to rapidly changing model architectures, traffic shapes, and hardware platforms — as opposed to the "Static Inference" era of closed models, single Transformer architectures, single-user workloads, and single-hardware deployments. Its flagship artifact is **Together Compiler (TKCC)**, an agentic "continual compilation" loop that uses swarms of optimization agents to recompile inference engines as traffic drifts — which Together describes as "the RSI moment for OSS models."

## The Static → Polymorphic Shift

Together's diagnosis, drawn from serving "many trillions of tokens per day":

| Trend | Evidence |
|-------|----------|
| **Model-release velocity** | 80% of OpenRouter traffic goes to models released in the last three months |
| **Architecture diversity** | None of the top-10 open-source LLMs on OpenRouter share an architecture (~11 years post-Transformer, no consolidation) |
| **Evolving traffic shapes** | Prompt lengths +80% within two weeks of a model release as users shift to agentic workloads; 1.4× prompt-length differences across countries (97k vs 70k); burstiness can double prompt lengths and collapse cache hit rates |
| **Hardware churn** | H100 → B200 → B300 → NVL72 → Vera Rubin, plus Groq and other alternative chips, each requiring distinct strategies |

Together explicitly calls out the legacy paradigm it is replacing: typical **vLLM / SGLang / InferenceX-AgentX recipes launch with static, hyperparameter-tuned engine configs**, and open-source kernels are frequently tuned against synthetic traffic (e.g., random tokens) that does not transfer to production — MoE kernels being the classic case, since expert-activation patterns are data-dependent.

Notably, Together self-critiques its own prior work: **megakernel fusion "is actually not the right design goal" for polymorphic inference** — their early production megakernels were painstakingly designed around a single static shape (batch-size-1 Llama 1B). This is a direct update to the [[concepts/megakernel-inference|megakernel debate]] of August 2026, and converges with Ali/waterloo_intern's "megakernels are dead" arguments and NVIDIA Rubin's tile-level dependency triggers.

## Together Compiler (TKCC)

TKCC recasts inference optimization "from a traditional compiler translation problem to an agentic search problem." Inputs: traffic shape, model, hardware. Output: a series of engine optimizations generated by agents, running in production on Together's most popular serverless endpoints.

### Three core design insights

1. **Persistent engines maximize experiment throughput.** Status-quo agent optimization loops relaunch vLLM/SGLang/TRT-LLM per experiment — 467 s to serving (process init 93s, weight loading 50s, KV sizing 21s, JIT warm-up 93s, autotuning 193s, API server 10s). TKCC starts the engine once and hot-reloads candidate forward passes: **9.0 s total** (RPC + setup 1.7s, CUDA-graph capture 7.3s). Multiple agents generate ideas in parallel, coordinating via a message board. Net effect: **252× higher experiment throughput** than baseline agentic optimization systems.
2. **A two-tier fidelity/throughput tradeoff.** "Fast engines" load a few layers for rapid iteration and low-variance timing; "slower engines" load many layers to validate optimizations against real data distributions. This matters because with data-dependent primitives (MoE, sparse-k attention) the input distribution determines which optimization wins — standalone kernel optimization on random inputs systematically misleads.
3. **A custom cost model selects parallelism strategies** (TP, EP, DCP, …) via tiered measurement — hardware specs → microbenchmarks → measured forward passes — pruning the configuration search space while capturing data-dependent properties (expert imbalance, prompt-length skew) that raw specs miss. The best layout shifts with concurrency.

### Results (vendor-reported — treat with caution)

All numbers below are Together's own benchmarks; no independent replication at time of writing.

- **Up to 2.6× higher TPS** in under 24 hours across frontier open-source models (Kimi K3, GLM 5.3, MiniMax M3.1-Flash, DeepSeek v4.1-Flash), starting from the best-reported open-source engine configs on [[concepts/ai-benchmarks/agentx-inferencex|SemiAnalysis InferenceX/AgentX]] — setting the performance frontier on all six model/chip pairs.
- **Low-latency batch-size-1 SOTA on InferenceX**: 1111 TPS (MiniMax M3.1-Flash), 1205 TPS (DeepSeek v4.1-Flash) — using the cost-model-selected parallelism instead of the InferenceX config.
- **1.7× TPS over open-source megakernels** on the canonical Llama 1B batch-size-1 workload (H100 and B200), holding up as sequence length grows.
- **Generalizes beyond LLMs**: on weather modeling, PDE, time-series, and biology codebases, TKCC finds larger speedups than Claude Code with `/goal` on three of four models — Together now uses it as a general-purpose AI compiler.
- Trainium2 numbers used a synthetic multi-turn dataset (70k ISL, 95% cached, 700 OSL) because the implementation didn't yet support higher concurrencies on limited HBM — a disclosed caveat.

## The RSI Framing

Together positions "getting AI agents to help optimize themselves" as a **recursive self-improvement loop for inference systems**: the serving stack that runs the models is optimized by agents (which are themselves served by that stack). This is an *infrastructure-side* instance of [[concepts/recursive-self-improvement|RSI]] — adjacent to harness self-improvement (Self-Harness, DGM) but targeting kernel/engine code rather than agent scaffolding. The bottleneck it attacks is the **speed of experimentation**, the same constraint Lilian Weng identifies for harness-engineering RSI.

## Research Agenda (announced alongside)

- **Self-serve Continuous Compilation** — customer-clickable optimization of dedicated endpoints (limited beta).
- **Shape-shifting speculative decoding** — draft model and lookahead adapting per-domain, per-request, per-token, and per load (vs. fixed spec-decode configs in vLLM/InferenceX/AgentX). Related: [[concepts/speculative-decoding]].
- **ThunderAgent Router** — dynamic routing across heterogeneous deployments/worker configs; ThunderAgent was an ICML 2026 Spotlight paper (see [[concepts/thunderagent]], [[concepts/together-ai-icml-2026]]).
- **Together Post-Training** — see [[entities/together-ai]]; partnerships with Moonshot, MiniMax.
- **TogetherLink** — workload-aware model routing/ensembling, rooted in Hazy Research's Ask Me Anything and Together's Mixture-of-Agents (ICLR 2025); the pitch: "ensembling a few pretty good models can outperform a singular great model."

## Assessment

- The traffic-shape evidence (regional prompt lengths, post-release prompt-length jumps) is a genuinely novel data release — inference providers rarely publish workload statistics.
- The InferenceX SOTA claims are vendor-reported against SemiAnalysis' benchmark; SemiAnalysis has not (yet) published an independent verification of TKCC's numbers. **Confidence: medium** on all performance figures.
- The strategic significance: if agentic compilation generalizes, hand-written kernel expertise (Together's own ThunderKittens moat) gets commoditized by experiment throughput — the same disruption logic the megakernel debate raised, now implemented in production by the megakernels' original authors.
