# MCP 2026-07-28 Specification Update

## Overview

**MCP 2026-07-28** is the fifth major specification release of Anthropic's [[concepts/model-context-protocol-mcp|Model Context Protocol (MCP)]], published on **July 28, 2026**. It represents one of the most significant architectural revisions in the protocol's history, moving MCP from a bidirectional stateful protocol to a **stateless request/response model**. This shift enables MCP servers to deploy on serverless and edge infrastructure, simplifies scaling, and aligns the protocol with standard HTTP workloads.

The release comes as MCP surpasses **400 million monthly SDK downloads** (a 4× increase in 2026) and Claude's connectors directory lists over **950 MCP servers** used by millions daily. Major industry players — including Figma, Intuit, Netlify, and Zoom — have been building on the new spec since beta.

### Key Changes at a Glance

| Dimension | Previous (pre-2026-07-28) | 2026-07-28 |
|---|---|---|
| **Protocol model** | Bidirectional stateful (HTTP+SSE) | Stateless request/response (Streaming HTTP) |
| **Transport** | HTTP + Server-Sent Events (SSE) | Streaming HTTP |
| **Session handling** | Persistent sessions with sticky routing | No session affinity required |
| **Deployment targets** | Long-running servers only | Serverless, edge, and traditional servers |
| **Extensions** | Ad-hoc, protocol-embedded | Versioned extensions framework |
| **Auth** | Varied implementations, workarounds for enterprise | OAuth 2.0 / OIDC aligned (Entra, Okta) |
| **New primitives** | Tools, Resources, Prompts | + Apps, Tasks, Managed Auth |

## Streaming HTTP Transport (New)

The most fundamental protocol change in MCP 2026-07-28 is the replacement of the deprecated **HTTP+SSE** transport with **Streaming HTTP**. Under the previous model, MCP servers used HTTP combined with Server-Sent Events to maintain a persistent bidirectional channel — the server pushed events to the client over a long-lived SSE connection while the client sent JSON-RPC requests over HTTP.

**Streaming HTTP** replaces this with a unified transport where both requests and responses flow over standard HTTP, with streaming semantics for real-time data delivery:

- **Single connection model**: No separate SSE channel required; streaming responses use chunked transfer encoding
- **Simplified infrastructure**: Works with standard HTTP load balancers, CDNs, and reverse proxies without SSE-specific configuration
- **Better compatibility**: Serverless platforms (AWS Lambda, Cloudflare Workers) natively support HTTP request/response but struggled with persistent SSE connections
- **Firewall-friendly**: Standard HTTP traffic with no long-lived connections to manage

This change was a prerequisite for the stateless architecture described below — SSE inherently required sticky sessions, which blocked horizontal scaling.

## Stateless Remote Servers

The move to a **stateless core** is the defining architectural shift of the 2026-07-28 spec. Previously, MCP operated as a bidirectional stateful protocol where the client and server maintained a session with shared state — the server knew about the client's connected tools, ongoing interactions, and conversation context.

Under the new model:

- **Request/response only**: Each MCP request is self-contained. The server does not retain client state between requests.
- **No handshake, no session ID**: Any request can hit any server instance. No session affinity or sticky routing is required.
- **Serverless-native**: MCP servers can run on AWS Lambda, Cloudflare Workers, and similar platforms that spin up instances per-request.
- **Horizontal scaling without complexity**: Load balancers distribute requests evenly; no need for session replication or shared state stores.

### Industry Impact

Netlify's VP of Applied AI, Sean Roberts, noted: *"The stateless core in the 2026-07-28 spec makes MCP a first-class HTTP workload with no session management to work around."* Zoom's Ross Mayfield added: *"The new MCP spec makes it far easier to deploy and scale MCP servers on standard HTTP infrastructure."*

## Session Management

Session management in the 2026-07-28 spec is **simplified and largely eliminated** at the protocol level. Key changes:

- **No mandatory sessions**: Servers are not required to maintain session state. Clients can include necessary context in each request.
- **Optional session tokens**: For cases where state is useful (e.g., authentication persistence), servers may issue opaque tokens that clients attach to subsequent requests — but this is an application-level concern, not a protocol requirement.
- **No session recovery logic**: Since servers are stateless, there is no session to recover after a restart or instance rotation. This eliminates a class of reliability bugs common in the previous spec.
- **Improved fault tolerance**: If a server instance fails, the next request simply routes to a healthy instance with no data loss or session re-establishment overhead.

For implementers, this means: drop the session management code. Stateless is the default; add state only when your application genuinely requires it.

## JSON-RPC Batching

MCP 2026-07-28 introduces **JSON-RPC batching** as a protocol-level optimization. Clients can now send multiple JSON-RPC requests in a single HTTP request body as a JSON array, and servers respond with a matching array of results.

This is particularly valuable in stateless deployments where each request incurs cold-start or connection overhead:

- **Reduced round trips**: Multiple tool calls, resource reads, or prompt fetches can be combined into one HTTP request
- **Atomicity hints**: Batching enables servers to process related operations together, though full transactional semantics remain application-defined
- **Lower latency**: For workflows requiring multiple MCP operations, batching avoids the cumulative latency of sequential HTTP calls
- **Compatible with streaming**: Batched requests can still return streaming responses where applicable

**Example batch request:**

```json
[
  {"jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {}},
  {"jsonrpc": "2.0", "id": 2, "method": "resources/read", "params": {"uri": "file:///data/config.json"}},
  {"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {"name": "search", "arguments": {"query": "MCP spec"}}}
]
```

## App, Task, and Managed Auth Primitives

MCP 2026-07-28 graduates extensions from ad-hoc additions into a **versioned extensions framework** with three new primitives:

### MCP Apps

**MCP Apps** enable servers to deliver interactive user interfaces directly within the AI conversation. Rather than returning only text or structured data from tool calls, an MCP App server can render charts, forms, kanban boards, and other rich interfaces inline. Apps use a `ui://` URI scheme and communicate via the `@modelcontextprotocol/ext-apps` SDK over JSON-RPC `postMessage` channels.

First proposed in November 2025 (SEP-1865) and officially released in January 2026, Apps are now a first-class extension under the versioned framework. Launch partners include Amplitude, Asana, Box, Canva, Clay, Figma, Hex, monday.com, and Slack.

### MCP Tasks

**MCP Tasks** expose long-running, structured work with well-defined inputs and outputs. Unlike one-shot tool calls, Tasks can span minutes or hours, report progress, and support cancellation. This enables workflows like:

- Batch data processing pipelines
- Multi-step agent workflows with intermediate checkpoints
- Scheduled or recurring operations
- Human-in-the-loop approval flows

Tasks ship under the same versioned extensions framework as Apps, giving developers a formal path to add long-running capabilities without modifying the core protocol.

### Enterprise-Managed Auth

Authorization in MCP 2026-07-28 is **hardened to align with production OAuth 2.0 and OIDC deployments**. This eliminates the workarounds previously required for enterprise identity systems:

- **OAuth 2.0 / OIDC native**: MCP servers connect to Microsoft Entra, Okta, and other identity providers without custom adapters
- **Admin-provisioned access**: IT administrators provision MCP connectors for their entire organization through the identity provider. Users inherit access through existing IdP groups.
- **Zero-touch user setup**: Authorized connectors are connected on first login — no per-user configuration required
- **Permission inheritance**: Agents inherit the same roles and permissions as the user's existing identity

This represents a significant evolution from the previous model where each MCP server implemented authentication independently, often requiring manual API key configuration per user.

## Comparison with Previous Spec

| Feature | Pre-2026-07-28 | MCP 2026-07-28 |
|---|---|---|
| **Transport** | HTTP + SSE (bidirectional) | Streaming HTTP (request/response) |
| **State model** | Stateful (server tracks client state) | Stateless (self-contained requests) |
| **Deployment** | Long-running servers only | Serverless, edge, traditional |
| **Scaling** | Sticky sessions required | Horizontal, any-instance routing |
| **Batching** | Not supported | JSON-RPC batching |
| **Extensions** | Ad-hoc (SEP proposals) | Versioned framework (Apps, Tasks) |
| **Auth** | Per-server implementations | OAuth 2.0 / OIDC standard |
| **Enterprise IdP** | Workarounds needed | Native (Entra, Okta) |
| **Session state** | Required; recovery logic needed | Optional; stateless by default |
| **Ecosystem maturity** | ~150M SDK downloads (early 2026) | 400M+ monthly SDK downloads |

## Migration Path

For existing MCP server and client implementers, the migration path depends on deployment patterns:

### For Stateless / Simple Servers
Servers that don't rely on session state (most tools, resources, and prompt servers) can migrate by:
1. Updating the SDK to the 2026-07-28 version
2. Switching transport from HTTP+SSE to Streaming HTTP
3. Removing session management code
4. Deploying to serverless infrastructure if desired

### For Stateful Servers
Servers that require session state (e.g., interactive workflows, progressive disclosure) should:
1. Evaluate whether state can be moved to the client (include context in each request)
2. If server-side state is unavoidable, implement application-level session tokens
3. Consider MCP Tasks for long-running stateful workflows
4. Test with load-balanced, multi-instance deployments

### For Enterprise Auth
Organizations with custom auth implementations should:
1. Migrate to OAuth 2.0 / OIDC flows
2. Integrate with their existing identity provider (Entra, Okta, etc.)
3. Enable admin-provisioned access for organization-wide deployment

### SDK Availability
Updated SDKs for the 2026-07-28 spec are available for TypeScript, Python, and other languages. Anthropic recommends migrating existing servers within the deprecation window for HTTP+SSE (timeline TBD).
