# Astro が Angular を葬った日 — 「人が好き」なフレームワークはエージェントが苦手 (2026-11-05 09:30 JST / morning)

**▶ 一言要約**: Nolan Lawson のベンチマーク (2026-10-28 公開、HN 2026-11-01 **378pts / 292c**) で、同一のポケモン風アプリを JS フレームワーク横断でエージェントに作らせたところ **Astro が最速・コスト2位**、**Angular が最下位** だった — フレームワーク選択の第一評価軸が「開発者の好み」から「エージェントの収束コスト」に移る転換点 [[concepts/ai-cost-of-js-frameworks]]。

## 数字が出た瞬間、議論は「好み」から「会計」に切り替わった

| フレームワーク | 結果 (HN スレッド集約) | 帰結 |
|---|---|---|
| Astro | 総合優勝: 最速 + 下から2番目のトークン消費 + クライアント JS ゼロ | スレッド合意で「エージェント時代のデフォルト」 |
| Angular | 最下位 | 「agents に対しても壊れているというデータが出た」(usernametaken29) |
| SvelteKit | 計測外の実価値あり | Zero-JS ≠ better UX (spieke)、progressive enhancement の価値は指標に載らない |

推定機序 (未検証、スレッド発): **人間の人気と相関する機能** — 重い DI/アノテーション層、暗黙の magic、大量の生成 boilerplate — がエージェントの混乱とリトライループを誘発する。明示的で単純なフレームワークほど収束が速い。これは [[concepts/token-economics]] をスタック選択まで延長した話で、グリーンフィールドのフロントエンドコードが大半エージェント書きになった 2026 年では、収束までのトークン差が API 請求書とレビュー往復回数に直接 compounded する。

スレッド内の反論も記録しておく。(1) skrebbel: ベンチマーク対象が content-driven = Astro の本拠地であり、realtime/async 主導のアプリでは順位が反転しうる。(2) ozim vs hajile の対立軸は「Angular が単純アプリでダメなら複雑アプリでマシになるのか?」— フレームワーク選択がスケールで重要度を増すか減らすかでスレッドが二分割された。**一次 URL が 2026-11-02 の取得時に 404** しており、フレームワーク別の正確な数値は HN スレッドからの再構成 (wiki 側 confidence: medium)。数値を引用する際は原典の再取得が必要。

## 対照実験: Figma の PM が Git で 31 個の skill を共有している

同じ「エージェント前提の運用設計」を組織側から実装した例が、Figma の **PM OS** (Ezra Mechaber 作、*How I AI* / Lenny's Podcast で 2026-11-02 公開) [[concepts/agentic-engineering/pm-os-shared-agent-skills]]。

| 項目 | 内容 |
|---|---|
| 中身 | Git リポジトリ 1 本 = `AGENTS.md` + **共有 skill 31 個** + command hooks |
| 規模 | 約 60–70 人のプロダクト組織 (GitHub 初心者含む) が自動バージョンチェックで同期 |
| 採用 | 3 人が Slack で PR を回す → 春のオフサイトで全员インストール → **roast 会**で生き残りを決定 |
| 計測 | 使用計測は意図的に **無し** (監視されている感覚を与えたくない) |
| 運用 | Ezra 自身はブラウザ操作が信頼できる水準になったため「ほぼ全時間 Codex」 |

設計哲学が鋭い。「PM が**サボるか下手にやる**仕事 (サポートのローンチ巻き込み、議事録、コンポーネントの owner 特定) に設計を寄せる」= lazy in the right places。そして Ezra は PM OS のベンチマーク作りを試みて**失敗した** — vanilla agent にどれだけ勝つかわからない。モデルが進化するたびに、居場所を失った指示を**削除**していく。これは [[concepts/agent-skills]] の個人セットアップを組織規模に上げた際の到達形で、「skill リポジトリはモニュメントでなく運用コンテキスト」という結論は [[concepts/skill-library]] の設計論にそのまま効く。

## 3つを結ぶ本日の読み — エージェント前提の「運用コスト」が意思決定の単位になった

朝の一枚として意識するのは、**評価対象が「人間の好み / 組織の慣習」から「エージェントが収束するまでのコスト」にすり替わっている**ことだ。

| 領域 | 旧来の評価軸 | エージェント時代の評価軸 |
|---|---|---|
| フレームワーク選定 | DX・人気・採用市場 | agent-legibility / token-cost-per-task |
| 組織の skill 管理 | ドキュメント量・属人化 | 削除され続ける運用コンテキストか否か |
| コードレビュー | 可読性・スタイル | レビュー往復回数 × トークン |

この切り替えに最も無防備なのは「ベテランの暗黙知」でできている層だ。[[concepts/sre-deskilling]] (SigNoz、2026-10-30 **605pts / 455c**) は Bainbridge 1983 の *Ironies of Automation* を引いて、自動化がルーチン認知作業を吸い取り人間に**稀で高リスクな危機だけ**を残す構造を指摘した。[[concepts/cognitive-surrender]] (Addy Osmani) が個人側の心理、[[concepts/ai-slop-productivity-paradox]] が組織側の請求書に対応する。PM OS が計測を意図的に捨てたのは、計測が暗黙知の提供を萎縮させることを知っていたからだろう — ここが同じ「運用コストの可視化」でも、トークン計算と人間相手の計算では最適解が逆になる箇所だ。

## 朝の 15 分 (今日やるなら)

## Caveats

- Lawson のベンチマークは **1 タスク・小規模アプリ** の単発実験。フレームワーク別数値は HN スレッドからの再構成で、wiki の confidence は medium。結果の一般化は待て。
- PM OS は Figma の**公式プロダクトではなく Ezra 個人の社内運用**。成熟度に差があり (AutoXP は「もう少し」、Jev 執筆支援は prototype)、他社移植の成否は未検証。
- 両件とも公開元が英語圏 1 次ソース単独 (nolanlawson.com / Lenny's Podcast)。独立した追試は現時点で wiki 上に未収録。
