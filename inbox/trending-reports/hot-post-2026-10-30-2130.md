# Hot Post 2026-10-30 21:30 (night)

## 💸 「観測機能は無償ではない」— Claude Code の30秒ポーリングが明らせた harness の請求書の盲区

**▶ 一言要約**: 背景エージェントのステータス1行を出すためだけに、全トランスクリプトを30秒ごとにOpusへ再送。検出したチームの計測では総支出の16.4%、入力:出力 = 9,000:1。

### 詳細

- 検出手法が本題。見つけたチームは Claude Code 自身の OpenTelemetry エクスポートを `query_source` でグルーピングし、harness 内部呼び出しをユーザー発の呼び出しから分離した。分離した瞬間、`agent_summary` がメイン会話(15.7%)を上回った。[[concepts/multi-agent-session-observability]]
- 3つの数字は矛盾しない。分母が違うだけだ。
  | 計測者 | 数値 | 対象 |
  |---|---|---|
  | DRIM / OTEL解析チーム | **16.4%**(全支出)、**19.7%**(全リクエスト) | 背景エージェント中心のチーム |
  | 個人テスター jakozaur | 最大 **~8%** | subagentのみ、workflowは無影響 |
  | Anthropic (Edwin Arbus) | **~2%** | ティーメトリ送信ユーザー全体の艦隊平均 |
  [[concepts/claude-code/claude-code-agent-summary-polling]]
- ベンダー側の説明は「意図した設計」。作業中の背景エージェントのみが対象で、idle は呼ばれない。要約はユーザーとharness両方がトランスクリプトを読まずに状態を追うための機構 — つまり漏れではなく仕様。
- 価格メカニクスの核心: **キャッシュヒットは無料ではない**。巨大なキャッシュ済みトランスクリプトの繰り返し読み取りにも課金される。コストは要約の出力長ではなく **トランスクリプト長 × ポーリング頻度** の関数。背景エージェントのキャッシュTTLは約5分なので、30秒ポーリングがヒットでいられるのはエージェントが動き続けているとき — /vendor が「ポーリングが発生する条件」と説明したケースそのもの。[[concepts/prompt-caching]]

### 深掘り

9,000:1 という比率は診断シグネチャとして使える。この入力対出力比は「モデルが判断しているのではなく読んでいる」リクエスト形状を意味する。設計上の誤りは polling(timer)で実装したことで、eventing(状態変化時に emit)であればコストは状態遷移回数に比例した。コンテキストが長大になる背景エージェントは、[[concepts/coding-agents/background-coding-agent]] が狙う長時間化の軸と費用曲線が完全に一致する。

既知の回避策は未検証のまま: settings の `disableAgentView`(呼び停止かパネル非表示か不明)、背景エージェントではなく通常セッションを使う、subagent より workflow を好む。スレッドでの懐疑は「そのうち安い decision model を出して解消する」というもの — 推論モデルと決定モデルを分ける発想は [[concepts/reasoning-models-from-scratch-course]] と同じ分岐。

## 🔍 反論: 16.4%を引用するな、分母を引用しろ

夜なので通説になっている数値を1つ疑う。HN 567pt / 230コメントまで上がった「Claude Code の支出の16.4%が内部ポーリング」という数字は、**背景エージェント中心のチームという最悪ケースの分母**で測られている。同じ機構の艦隊平均はベンダー計測で ~2% だ。

16.4%と2%の両方を同時に成立させる分母の差を明記しない引用は、どちらの側にとっても誤解を生む。今後の引用は「16.4%(背景エージェント中心チーム)/ 2%(艦隊平均)」のように単位をセットにする。

これは [[concepts/harness-tax]] が示した結果と同じ形をしている。同一モデル・同一成功率帯でも harness 間のコスト差は最大5倍(Claude Fable 5: Claude Code $1.33 vs Pi $0.67)、対して成功率への harness 効果は ±2%。つまり **harness は正しさより請求額を決める**。16.4%の話はその下位ケース — ステータス表示という、タスク成功率に一切効かない機能が課金されている。

同じく可視化されていないコストとして [[concepts/harness-engineering/agent-execution-tax]] がある。ここでも問題は知能ではなく実行側だった: 構造化出力の不正で Gemini 2.5 Flash は 22.9% の実行税を払い、Kimi K2.5 は 0.0%。3つの概念に共通するのは **「ユーザーが払っているつもりっていない分のコストが、harness 側の attribution が無いと観測不能」** という一点だ。

検出に必要だったのは高性能な監視ではなく `query_source` による1列のグルーピングだった、という事実は逆に痛い。**harness 内部呼び出しをユーザーターンと混ぜて出力している実装は、自社のコスト構造を自社でも見えないようにしている。** Codex CLI / Cursor / pi が同じ方式でポーリングしているかの比較データは無く、wiki の open question のまま。[[concepts/harness-engineering/agent-harness]]
