## ▶ 一言要約: 先週出た2社のYCエージェント基盤スタートアップは、どちらも「モデルが本体・自分はインフラ」という建前を捨てていた — Maritime は sandbox を「問題の10%」と切り捨て、StarSling は「CI請求書が推論請求書に近づいた」と自白する

## 詳細

今朝の枠は Together AI のエージェント起因 credential leak ([[concepts/agent-credential-leasing]] 側面) を扱った。夜間枠なので、同じ週の wiki で最も逆張り的に読める2ページを並べる — どちらも Launch HN 単一ソースなので、以下の数字はすべて企業自己申告として扱う。

### Maritime (YC F26) — "$20/month の製品に $29/month の sandbox は載らない"

- 創業者 Ary / Maria は MIT **Project NANDA** 出身。agent-building 企業 ~200社へのヒアリング結論が「sandbox を選んでも残り90%は自分で作るはめになる」([[concepts/managed-agents]], [[concepts/agent-native-cloud]])
- SF sandbox Boom への直接批判: 「Hetzner/OVH の bare metal を Firecracker で切って低マージンで売るだけ」([[entities/e2b]], [[entities/daytona-sandbox]], [[entities/modal-sandbox]]) — つまり [[comparisons/agent-sandboxing]] の既存プレイヤーを「VM リセラー」と呼ぶ位置取り
- 数字の核心: $0.04/hour 常時稼働 = 約 $29/month > 個人向けエージェント製品の価格 $20/month。推論もストレージもまだ載っていない
- 対案価格が **2GB RAM エージェント 1台 $1/month・使い放題**。仕組みは scale-to-zero + copy-on-write + compressed memory snapshot + hot/warm/cold tiering
- この $1 は技術力ではなく **前提条件への賭け** — エージェントは大部分 idle で event-driven でなければ破綻する ([[concepts/agent-orchestration-runtime]])。常時 active な coding agent を載せた瞬間に model card と請求書が噛み合わなくなる
- HN 60p。Launch post のみ、Q&A は未採掘

### StarSling (YC P25) — 「CI請求書 ≈ 推論請求書」の初公開

- 創業者 Yonas (StackShare, 1.5M devs) / Daniel (ex-Netflix developer portal)。自社エージェントが大量 PR を出しすぎてジョブキューが数時間詰まり、**CI 請求書が推論請求書に近づいた** — agent-volume repo の費用構造を public にした最初の級の事例 ([[concepts/token-economics]])
- 提案は「CI 上で [[concepts/karpathy-loop]] を回す」: workflow・ログ・telemetry を解析 → 最適化案 → 変更なし workflow と side-by-side 実行 → **統計的有意性を決定論的に判定** → 証拠付き PR として ship ([[concepts/autonomous-component-optimization]])
- 検証ゲートが "LLM-as-judge" ではなく deterministic A/B である点が、単なる「CI を速くしてとエージェントに頼む」との差別化。同一ループが better-auth で **11か月放置されたボトルネック** を発見し、テスト1ジョブを 5.4× 高速化 (PR #10762)
- 申告ベンチ: Mastra 月 **1,800+ merged PRs**、最遅 workflow 29m56s → 5m06s (5.87×)、OSS 平均 wall-clock ~10× / runner time -70%。mirotalksfu 36.4× など repo 間分散が大きいので平均値は鵜呑みにできない
- 「速い HW は table stakes、要るのは改善を止めない process」— OpenAI / Anthropic / Linear の CI 最適化を agent 可読な playbook 化 ([[concepts/harness-engineering]])

### 2社を横に並べて言えること

| 観点 | Maritime | StarSling |
|---|---|---|
| 売り物 | 実行環境 (lifecycle/snapshot/tiering) | 改善ループ (deterministic A/B CI) |
| 主戦場の変更 | コンピュータ → storage tier hit rate | LLM judge → 統計検定 |
| 経済の賭け | エージェントは大部分 idle | エージェントは大量 PR を出し続ける |
| 既存市場への批判 | sandbox = VM リセール | GitHub Actions runner |
| HN 反応 | 60p | 89p |

逆張りとして成立するのは、両社が「エージェントの知能」を全く売っていない点だ。Maritime の差別化は memory snapshot の圧縮と tier hit rate、StarSling のそれは LLM judge を避けた deterministic significance test。[[concepts/land-rush-cicd]] のエージェント大量投入局面では、制約はモデル能力ではなく [[concepts/code-review-bottleneck]] より下流の計算・ストレージ・検証 throughput に移っている — 2社はその同じ前提の、上側と下側を別々に売っている。

## 深掘り

Maritime の $1/month は「1台あたり」であり、idle 時間課金ゼロの tiering が前提。hot snapshot を RAM に載せた瞬間に hot tier の価格曲線に戻るため、$1 は wake latency をどこで切るかの関数になる — 「unlimited usage」との両立は cold tier 命中率の統計に依存する。StarSling 側は deterministic gate が無いと agent が自分の benchmark をよく見せる方向に最適化される ([[concepts/llm-evaluation]] の regression gate と同型) — ループを自動 merge まで進めるか、提案止まりにするかでリスク性质が変わる。CI 側は deterministic で担保できているが、レビューする人間がいないと「意味の無い高速化」の PR 洪水になる点が [[concepts/code-review-bottleneck]] に跳ね返る。
