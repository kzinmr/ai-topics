# 🧠 AI Brain Fry の解法は「gitを優先度キューにする」こと — 20スレッド脳内RAM問題の構造化

**▶ 一言要約**: Sergey Kuhne の brain-fry 対策は、全チケットを git 上の markdown ファイルとして保持し、エージェントがボードを巡回、人間は「owner inbox」に出た判断項目だけを1枚の artifact ページで1件ずつ処理する設計 — コンテキスト保持を脳から git に移した (HN 50416363)。

## 仕組み (How I Fight AI Brain Fry)

- 元記事: https://sergeykuhne.com/blog/fighting-ai-brain-fry (HN 50416363, 2026-11-09)
- 診断: 並列エージェント作業の破綻要因は **sequencing と context** の2つ。20スレッドを「脳内RAM」に保持する状態が focus を壊す
- 対策の4要素:
  1. **キューを git に置く** — チケット=リポジトリ内の markdown ファイル、ボード状態はコミット済みスナップショット。チャットウィンドウにも頭の中にも何も置かない。セッションが死んでもキューは残る
  2. **エージェントがボードをサイクルで巡回** — 新チケット調査、人間が safe タグしたもののビルド、テスト+ブラウザチェック、デプロイ済み検証。機微コードはブランチで要事前許可、本番デプロイは人間のみ
  3. **判断だけ人間に集約 (owner inbox)** — スクリプトがボード全体を読み、「私の判断を待っている項目」の優先付きリストだけを生成。レビュー対象は git から再構築される1枚の Claude artifact ページ (ビューアであって記録ではない)
  4. **「閉じる」が核心** — 1件文脈を読み、判断し、キューに戻して閉じる。未決事項が記憶に残らないので次の1件に集中できる
- 残課題: チケット読み込みを20分→1分にすること、と「自分の裁定待ちで無限ループするチケット」の対策
- 著者自身の評価: 「依然として消耗する。しかし見失わない (I don't feel distracted or lost)」

## 導入する際の注意点

- 前提条件: チケット粒度が「1件の裁定で閉じる」サイズに分解できていること。分解できない大型タスクには不向き (著者も blocked-loop を課題に挙げる)
- artifact ページはビューア専用に徹すること — 記録が2か所に分かれる瞬間に git の単一真実源性が壊れる
- 検証は agent 任せにせず test + browser check + デプロイ検証の3層をサイクルに組み込む ([[concepts/evaluation/evals-how-to-know-whether-an-ai-system-works]] の「grader を疑え」の実務版)
