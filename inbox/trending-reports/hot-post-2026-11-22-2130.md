# ZDR は「最初のホップにしか効かない」— 200万 canary が暴いた推論チェーンの実測値

夜間スロット、振り返り・逆張り视角。今週の wiki で最も重い一枚はモデルでもベンチマークでもなく、[[concepts/dragos-inference-canary-study]] の監査設計そのものだった。

## ▶ 一言要約: 200万 canary プロンプトの実測が示した結論 — ZDR は契約上の最初のホップで終わり、最後のホップは「最安値」が決める

## 詳細

- **攻撃者は侵入済みの場所で待っていた**: 数百個の Dragos 製 AWS key を各 1 リクエストだけ送ったところ、10 月下旬の短時間に全滅。盗まれたリクエストには**モデルが走る前に拒否されたもの**が含まれる = 推論スタックの手前、プロバイダの「表口」でコピーされていた。
- **ZDR フラグは守らない**: 中国系 AI ラボのシステムは 7〜10 月に自モデル向けプロンプトの **>50% の URL を取得**、そのうち **約 2/3 は "no data collection"/ZDR 指定**。米リセラー経由のリクエストでも同じスクレイパーが発火している。米ホスティングを払っても米国内処理は買えなかった。
- **保存はリクエスト意味論の外側で行われる**: 単一の検索エンドポイント呼び出しから **2 か月以上**シークレット URL をクロールし続けた米大手、24 日後に中国 Feishu の社内チャットでシークレットリンクが再出現(2 分以内に 3 PC + 3 スマホで open)。ZDR は per-request の語義しか持たず、dataset・cache・log・search index は対象外 — [[concepts/zero-data-retention]] が列挙する「side doors」。
- **利益相反を認めた上で価値がある**: Dragos は runZero 系ベンダー( interested party )、プロバイダ名は仮名化、独立検証なし。それでも方法論(AWS key + DNS + URL を全プロンプトに埋め、受け手を全部自分で運用)が再現可能であり、[[entities/together-ai]] の 6〜7 月サンプル流出で盗まれた credential 5 個が **Dragos canary と一致** = 野生のシードが実際に生きている相互確認が取れた。

## 深掘り: 市場の反論 — OpenRouter の「政策執行者」転換

同じ ecosyste を告発された [[entities/openrouter]] は翌日(11/22、HN 159)に "Data Processing Incidents on Inference Providers" を出し、**3 プロバイダ off-board / ZDR 適用対象 125 endpoint 削除**(研究者指摘分+予防的)/ 影響可能性のある顧客へ通知を実施。canary 検査を常時運用に組み替え、ZDR 復活には検証を要求する方針。「AI の Stripe」から「ZDR を執行する上のレイヤ」への自己位置づけの書き換えであり、[[concepts/ai-supply-chain-security]] の議論で router を単なるコスト最適化装置と見るか信頼境界と見るかの分岐点になる。

| 論点 | 市場の建前 | 監査の実測値 |
|---|---|---|
| ZDR | プロバイダが保存しない | ZDR 指定の約 2/3 がスクレイプ対象 |
| Router | 単一の信頼できるホップ | 非公開ホップ多段、広告パス外の送信 |
| 最安推論 | 効率化 | 盗難 AWS credential で請求される容量 |
| セキュリティ設定 | 検証済み | 検証手段は顧客側 canary のみ |

## 残る欠落

ZDR の「保存しなかった」を証明する仕組みが存在しない — HN での指摘どおり Apple Private Cloud Compute 級のハードウェアアテステーションなしには、末尾ホップの ZDR は trust-me marketing のまま。顧客側に残された唯一の監査は自分で偽 credential を撒くことで、これはつまり**推論チェーンの信頼性が、プロバイダの規約ではなく顧客の攻撃的テストに外注されている**状態を意味する。
