# 🏆 「slop cannon」を止めた3つのゲート — Warpが公開したfactory-as-codeの実装手順

朝イチの1本。[[concepts/dark-factory-software-factory]] の議論は「人間はレビューするか」に集中しがちだったが、Warp (Ben Holmes, 2026-11-24) はレビューの前に **3つの機械的ゲート** を置く設計を、YAMLそのもの付きで公開した。backlog自動化が「誰も読まないPRを撃ち出すslop cannon」に収束する経路への、実測ベースの処方箋になる。

## 1. blueprint YAML — ワークフローをコードにする

**▶ 一言要約**: factoryの実行単位は `worker`×`stages` のYAMLで、各stageに `inputs`/`outputs`/`prompt.file`/`to` を宣言する。foreman(対話)とbuilder(実装)でcontext windowを分けるのが最小構成。

**詳細**:
- 3手順をmarkdown skillに書くのが出発点だが、入出力の形を強制できない。YAML化により (a) 各実行が同じ形の結果を返す (b) ステージ進行を可視化・デバッグできる、の2つの利得が出る
- trigger は GitHub の `issue_labeled` + `labels: [factory]`。issue本文がそのまま `request` inputになる
- 費用の実数: このfactoryの「小さく定義済みの修正」は open-weight モデルで **1 issueあたり $1 未満**。深い機能開発は第二の目が必要、と記事自身が線引きしている
- Warp Factories 側の公称値は約30%の社内タスクをautomation済み([[concepts/warp-factories]])

出典: [[raw/articles/2026-11-25_warp_program-software-factory-as-code]]

## 2. triage + spec gate — 実装前に人間判断を差し込む

**▶ 一言要約**: 「expand all」のissueで実装エージェントが3つの質問(配置場所/適用範囲/展開中に開いているファイルの扱い)を逆質問してきた。3つ目は投稿者も考えていなかったedge case。

**詳細**:
- backlogエージェントは曖昧さをおかまいなく実装する。これがslop cannonの発生機
- triage stageは3経路router: (1) 定義済み変更→実装へ直行 (2) プロダクト判断が残る機能→spec stageへ (3) 実装不要の質問→handoff
- specは**コードとしてcommit**する方針(Warpのopinionated take)。検証セクションが後のチェックリストになる。承認済みspecが implement の inputに入る
- 「grill me」型質問は Matt Pocock の `/grill-me` skill と同じ形([[concepts/coding-agents/code-review-agents]] に用途別使い方、[[entities/micahflee]] に実運用導入例)。[[concepts/spec-driven-development]] の precise incompleteness(過小指定も過大指定も失敗)の実装版
- 効果の判定は「コードが出る前に質問が返ってくるか」。実装後のレビューで問題発見するより上流

## 3. computer-use検証とmerge-risk 5項目 — PRを出す前に証明させる

**▶ 一言要約**: 「自分のマシンで試していない同僚のPRをレビューしたいか?」という問いに対し、エージェントにはそれを許してきた。UI verification skillでアプリを起動→操作→録画し、PRにVisual proofセクションを貼らせる。

**詳細**:
- skillの中身が実運用の化石層になっている: 「右クリックは synthetic contextmenu ではbase-uiのメニューが開かない。実際の `Input.dispatchMouseEvent` が要る」「スクショは DPR 2 (CSS px × 2)」— エージェントが検証中に発見した gotcha をskillに追記し続ける
- merge-risk assessmentは5カテゴリ: **Alignment**(PR説明にない drive-by 変更の有無)/ **Impact**(blast radius、auth・permission・schemaに触れるか)/ **Verification**(CUA・E2E・unitで検証済みか)/ **Rollback cost**(two-way door か destructive schema の one-way door か)/ **Error detection**(monitoringに出るか、握りつぶされるか)→ low/medium/high 判定
- さらに **実装者にPRを開く前にこのskillを実行させ**、リスクを先に潰させる(不足ログ追加、検証証拠の収集)。Impact と Rollback cost をPR本文の sectioned heading にする
- 「slop cannon」の語は [[concepts/agent-slop]] の信頼性ギャップ議論、レビュー側の壁は [[concepts/code-review-bottleneck]]。CUA自体は [[concepts/computer-using-agent]]

## 4. 収束点 — factoryはCI/CDになるか

**▶ 一言要約**: Warpの主張は「factoryはSaaSでもAIチームメイトでもなく、CI/CDのようにその上に作るインフラ」。裏付けは factory-as-code(agent自身がfactory定義にdiff PRを出す)と multi-model routing。

| 項目 | 数字 | 出典の種別 |
|---|---|---|
| 小修正のissue当たりコスト | < $1 (open-weight) | Warp自計 |
| 社内タスクのautomation率 | 約30% | Warp公称 |
| 競合比のスループット | 約1.6×/node (同一p99ターゲット) | [[raw/articles/2026-06-03_hornet_agent-queries-cost-more-to-serve]] |
| cost-per-PR (2026-10時点) | $80 → $30 | Warp公称 |

- 3番目の行だけWarp以外の独立ソース([[raw/articles/2026-06-03_hornet_agent-queries-cost-more-to-serve|Hornet]] の BrowseComp GPT-5エージェント計測)で、エージェント実行の重い部分はコード生成より**検索・読み取り側**にあることを示す。factoryの最適化対象は生成ステージだけではない
- 留保: 上表のWarp系3行はすべてベンダー自己申告。閉 Beta、$10k credit の初期段階で、throughput/ROIの実測は外部未検証。`Don't vibe code your software factory`(11-04) を含む6本の記事シリーズは結果的に同社の course + demo 導線になっている

**深掘り**: 「observerエージェントがfactory定義にPRを出す」自己改善ループ([[concepts/self-evolving-agents]])は、コードではなく**ワークフロー定義**が変更対象になる点で通常のlint-feedback-loop([[concepts/coding-agents/lint-rules-as-agent-feedback-loop]])と階段が違う。失敗時の局所化がops上の一等問題になる — どのstageのどのinputが悪PRを作ったかをtraceできるかどうかが、YAML blueprintの本当の検収基準。
