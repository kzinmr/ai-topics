# Hot Post 2026-10-29 01:30 JST (late-night)

## 検索インフラは「エージェント前提」で作り直されている — 同一エンジンでQPS 8.4倍差

**▶ 一言要約**: GPT-5エージェントの検索クエリは人間の中央値2語の99パーセンタイル超(10語)。同一エンジン・同一HWでserving capacityがAOL人間3,236 QPS → BrowseCompエージェント384 QPSと8.4倍落ちる。

**詳細**:
- 出典: Jo Kristian Bergum (CEO, [[concepts/hornet|Hornet]])「Agent queries cost more to serve」2026-06-03。raw: `raw/articles/2026-06-03_hornet_agent-queries-cost-more-to-serve.md`。詳細は [[concepts/agentic-retrieval]]
- 実験条件は固定 — Hornetエンジン、100M Common Crawl WET文書、AWS Graviton4 32vCPU/128GiB 1台、BM25(body) top-10。変わったのはクエリ workload だけ
- 人間 vs エージェントのクエリ長: 中央値 2語 vs 10語、p90 5語 vs 17語、初回クエリ平均19語、最大78語(GPT-5 BrowseComp-Plus 830問・19,279検索コール)
- 演算子の使い方自体が人間と別物: phrase quote 65.56%、4桁year 45.60%、`site:` 6.43%のクエリ。1セッションではphrase quote 98.19%、year 95.42%
- 1問あたり検索コールは中央値24回(p90 35、max 63)。各コールが次の文脈になるため、3ターン目の取りこぼしが以後全ターンに伝播する
- 容量が尽きる原因は「トラフィック増加」より「ミックス変化」が多い。高频語phrase照合は低频語ANDよりCPUが高い — 現実的クエリミックスでのベンチ必須

| Workload | QPS (<500ms p99) | 人間比 |
|---|---|---|
| AOL 人間キーワード | 3,236 | 1.0× |
| MS MARCO 人間質問 | 1,151 | 0.36× |
| BrowseComp GPT-5エージェント | 384 | **0.12×** |

**深掘り**:
- 検索が律速であることは oracle 比較で定量化されている。BrowseComp-Plus で GPT-4.1 は hand-picked evidence(oracle retrieval)で93%、weak BM25 baselineで14% — 79pt差が retrieval bottleneck。128k context windowはコーパス(100,195ページ/736M token)の0.017%しか入らず、1Mでも0.14%。「長時間windowで検索を回避」は構造的に不可能
- Hornetの設計思想は「dumb client, smart server」の反転。エージェントは smart client なので、schema-first API・verifiable な retrieval・self-host・model-agnostic を前提に作る。API surface を「coding environment のように」見せるのは、frontier modelがRLで code execution / filesystem 経由の推論に最適化されているため — [[concepts/filesystem-memory]] と同じ設計収束
- 企業KB側の実装も収束している。[[concepts/enterprise-knowledge-base-architecture]] の Cerebras KB(15,000+ queries/day)は LLM planner → 並列fan-out(RRF検索 / Slack / `rg` / Who-Knows) → 小型reranker(0-10点、top-10) → synthesis+context expansion。检索 primitive を MCP で公開する構成
- 注意: 8.4倍・79pt・0.017%はいずれも Hornet 側の自社エンジンベンチおよび BrowseComp-Plus ベースライン。エンジン選定を伴う数値であり、他エンジンでの再現値は wiki 未収録
