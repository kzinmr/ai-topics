# 🔍 「AIが書いたコード、誰がレビューする?」問題に Warp が3レバー回答 — Jellyfish +30%/-0% データの処方箋

**▶ 一言要約**: Jellyfish telemetry調査(700社・3億work events)はエージェント採用でLOC +30%・PR +23%なのに出荷ソフトウェア増加ゼロを示した。Warpは11/5付で、ヒトレビュー時間を削る3レバー(敵対的レビューループ / computer-use検証 / /merge-risk 5項目スコアリング)を公開。

## 背景: ボトルネックは「書く」ではなく「見る」に移動した

[[concepts/code-review-bottleneck]] の中核データ(Chen & Stratton, Harvard + Jellyfish、2021〜2026/3):

| 指標 | エージェント採用後 |
|---|---|
| 生成LOC | +30% |
| コミット | +20% |
| PR数 | +23% |
| 正味の出荷ソフトウェア | 増加の証拠なし |
| エンジニア人数 | 削減の証拠なし |

コードを書く工程(最も安価)をAIが圧縮するほど、制約は最難関のシニアレビューに集中する — 組織の制約理論そのもの。問題は「ではどう削るか」で、その実装レシピが今回初公開された。

## Warp が示した3レバー (Warp Factories の本番構成)

1. **自作レビューエージェントによる敵対的プレレビュー**: 実装エージェント→レビューエージェントが「severity/impact/修正案」付き所見リストを往復し、Nターン上限まで反復。GitHub PRに全コメントを流さず、人間入力が要る所見だけスレッドに出す。Addy Osmani が指摘した通り、本番インシデントとrevertを高シグナル評価ケースに変換してレビュー精度を上げる([[entities/addy-osmani]]、Anthropic internal code review process)。
2. **computer-useによるエンドツーエンド検証**: staging DB起動・テスト資格情報注入・アクセスログ採取をバックエンドで、クライアント側は仮想デスクトップで実アプリを操作([[concepts/computer-use]]、[[concepts/webmcp-protocol]] 経由)。検証成果物(スクショ+録画、before/after必須)をPR必須フィールド化。録画はFFmpegで無操作区間を自動カットし数分→10〜15秒に圧縮。過剰検証の抑制(重複フローのスクショ禁止)まで設計に含む。
3. **/merge-risk スキルで5項目スコアリング**: Verification / Alignment / Impact(auth・billing等の機微経路はcode ownerへルーティング)/ Rollback cost(Matt Pocock の one-way vs two-way door 枠組み)/ Error detection([[concepts/sentry]] webhook をエージェントに中継し自走修正)。高リスクPRにだけ人間の注意を配る。

## 効きそうな論点と留保

- **レビューにもハーネスが必要**という主張は [[concepts/harness-engineering]](Hamel Husain の60-80%則)と同一線上。ただし Warp は「レビューの多段化」を提案しつつ、コスト対品質ベンチマークで**大型機能のみ多段レビューを適用**するゲートを実験中 — [[concepts/harness-tax]] が指摘する自己反証パターンがここでも起きている。
- LLM-as-a-judge + 自己改善エージェントでレビュー品質自体を評価する構成は [[concepts/dark-factory-software-factory]] の観測可能性要件そのもの。Sentry→エージェント中継はエラーフィードバックループの実装済み事例。
- Warp 自身が「人間のボトルネックは消えない」と明言している。+30%/-0% のギャップを3レバーでどこまで潰せるかは未検証(11/10のライブセッションで追加データ公表予定)。
