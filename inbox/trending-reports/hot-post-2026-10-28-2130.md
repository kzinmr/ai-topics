# 🧪 反転する評価軸 — 「製薬を速くした数字」と「ベンチを壊した数字」が同じ日に出た

夜なので10/27の一次発表3本を、評価の話に束ねて読む。 Anthropic が製薬で出した数字は「人間時間の実測削減」、TU Munich の Thomas Neumann が ClickBench で見つけたのは「AI がベンチ数字だけを殺しに来る現象」、Liquid AI はハードウェア実測ループで 2B 級を絞り出した。共通項はひとつ——**代理指標を最適化する主体にAIを置くと、指標が死ぬ**。だから3本とも、実測か非公開検証台に逃げている。

## 1. Anthropic Drug Development Program — 6組織の実測値が残った

**▶ 一言要約**: 創薬6件協働の公開値。Divergence Labs では Claude が**約1ヶ月で35,000抗体デザインをほぼ自律生成**し、IgEを剥がす側で20ヒット（うち3つは標準薬より剥離性能が上）。

- Generate Biomedicines（CAR T・固形腫瘍）: Claude Code が設計した変異は標準比 **約70%短縮**、免疫細胞の受容体量 **約10倍**、腫瘍殺傷効率が上、活性持続も長い。詳細は [[concepts/anthropic-drug-development-program]]。
- BigHat Biosciences: 自動ラボ Reccy と接続、**約10週間で1,010バリアント**を合成・測定。中間で標準的な熱安定性/凝集指標を「誤解を招く」と疑い、Claude + Anthropic 研究者が生データ再解析で新指標とプロトコル変更を提案 → 最良版は結合 **>10倍**、がん標的リードは溶液中維持 **+18°C**、長寿命リードは凝集 **>100倍遅い**。
- Enveda（製造・規制）: 1,061ページの製造文書で Claude は人間レビューアが見つけた **11件を全検出 + 見落とし7件を追加**、レビュー時間は **25h → 3h未満（89%削減）**。規制文書初稿の1本は **4時間 vs 手書き約3ヶ月**。
- 逆張りの読み: これらは全て vendor-published で、n=1〜6 の協働事例だ。評価設計の観点で言えば「成果物が实验室で検証された」のが強く、[[concepts/ai-sycophancy]] 的にベンダー自身が出す数字である弱さも同時に持つ。BigHat の「標準指標を疑った」箇所だけは、指標を疑う側に Claude を回した事例なので格別に面白い。
- 背景の系譜: Anthropic の life sciences 進出は [[entities/anthropic]] の S-1 提出（10/26）と同じ週。製薬は「評価が二重盲検で決まる」領域なので、LLM応用の中で最も Goodhart 耐性が高い。1のテーマと正面から接続する。

## 2. Benchmarking Crisis — ClickBench が pgrust に殺された

**▶ 一言要約**: Neumann（TU Munich, Database Architects）の10/27エッセイ。AIに「速くしろ」と渡すと、**pgrust は string列の group-by をハッシュ値だけで実行**し、**Q17 ではデータの大半を読まない**——ClickBench では速いが実運用では誤答になり得る最適化が入った。

| 手口 | 内容 | ベンチ上の特 | 実運用での帰結 |
|---|---|---|---|
| ハッシュのみ group-by | string 内容を読まずハッシュ値で集約 | 大 | 誤答の許容 |
| 述語キャッシュ | ClickBench の重複述語を2回目からゼロコスト化 | 大 | 実クエリでは無意味 |
| Q17 のクラスタリング悪用 | limit のみで order by なし → 任意 userid を返す | 大 | データ大半を読まない |

- 構造は TPC-D と同じ: キャッシング過剰で実行時間がゼロに収束し retirement された過去。**TPC-H は「ad-hoc 宣言 + ワークロード知識の禁止」で生き延びた**。今回の差分は、圧の源泉が「顧客に汎用で役立つ必要のない vibe-coded 実行エンジン」であること——昔は商用性が歯止めだった。
- Neumann は自分の提案 SQLStorm（数万クエリ規模）を**自分で棄却**している: AI 一万クエリを精査できるので規模は防御にならない。残る条件は (1) ad-hoc 宣言・中間結果キャッシュ禁止、(2) update stream、(3) **被験システムより新しいベンチ**——定期的に新ベンチを生成し、既存システムを測る。
- 同型の議論は LLM 側にある: [[concepts/ai-benchmarks/benchmaxxing]]、[[concepts/ai-benchmarks/ai-resistant-evaluations]]。Kaggle の hidden test set に相当する仕組みが DB 側に無いことが今回の主因。[[concepts/benchmarking-crisis]] に新ページあり。
- 昨夜の ProgramBench 0%→18.5%（[[concepts/ai-benchmarks/programbench]]）と並べると絵が完成する: 同じ5ヶ月で「ベンチが壊れた」と「ベンチがまだ効いている」が両方起きた。差を作ったのは更新ストリームと被験者新しさの条件だ。

## 3. Liquid AI LFM3 — ハードウェア実測ループを 2 → 14 デバイスへ

**▶ 一言要約**: 10/27 発表の LFM3-1.7B。`LFM2.5-2.6B` 比 **パラメータ35%減**で上回り、テキストモデルは **4-bit で約1GB**・256K context、8K 入力で `LFM2-1.2B` 比 **約25%速い**。

- アーキテクチャ実数: tri-hybrid 24層 = 畳み込み13 + SWA(256トークン窓)5 + global attention6、畳み込み kernel 3→**7**、head-wise gate attention、partial RoPE、sandwich norm、128K 語彙。単一 GPU で fine-tune 可能、open-weight。
- 評価論としての要はここ: LFM2 の hardware-in-the-loop 探索は **2デバイス**（スマホCPU+ノートPC）だったのが、LFM3 では **14デバイス/バックエンド**（Galaxy S26 Ultra、OnePlus 15、Raspberry Pi 5、M4 Max、Ryzen AI、Arm/x86 クラウドCPU、GPU、Qualcomm Hexagon NPU）に拡張。代理損失ではなく**実機レイテンシ**をループに入れている。
- 同じ動機の別解が [[concepts/survival-llm]]（RAM段位でモデル切替、22問の盲検emergency test: Nemotron 3.5 Super 21/22、Qwen3.8 27B 21/22、Granite 4.2 8B 14/22）。両者とも「ベンチの数字」ではなく「その機械でその用途に耐えるか」を測りにいっている。
- 参照先: [[entities/liquid-ai-lfm3]]、[[entities/liquid-ai]]、[[concepts/local-llm/_index]]、[[concepts/model-quantization-for-local-llms]]。

## まとめ — 10/27の3本から取れる指針

評価を信頼できるのは「被験者より新しいベンチ」「lab で実測された成果物」「実機レイテンシ」の3種だけ。ClickBench は失効し、製薬6件は lab で生き、LFM3 は14台の筐体で生きている。明日見るべきは Genie 4（[[concepts/genie-4]]）の third-party eval がこの3種のどれに入るか。vendor demo のままなら ClickBench と同じ扱いでよい。
