# 遅延の原因は遅いGPUではない — 「考えること」自体が時間超過 (2026-11-04 01:30 JST / late-night)

**▶ 一言要約**: [[concepts/ai-benchmarks/realtime-bench]]（arXiv 2610.22155、UT Austin/Ohio State/UIUC/NVIDIA/Northwestern/Steadyworks、50課題）は同一モデルの成功率を Wall Clock で **44%（Pass^3 36%）**、Paused Clock で **70–80%** に分けた — 能力はあり、時間規律がない。

## Token Clock という発明 — CoT を「時間コスト」として課金する

既存の"real-time"評価はストリーミング知覚と会話品質を測るだけで、**間に合うか**を測っていなかった。Realtime-Bench が足したのは3つの能力軸と3つの時計条件。

| 時計条件 | 挙動 | 分離したい変数 |
|---|---|---|
| Wall Clock | 実レイテンシで環境が進む | 実運用性能 |
| Paused Clock | 推論遅延を完全除去 | 理想化された能力基準 |
| **Token Clock** | **トークン生成ごとに模擬時間を固定レートで進め、コミット時点の時刻でアクション適用** | 「時間理解の欠如」と「考えすぎ」の分離 |

Token Clock の狙いは hardware 除去にある。GPU が速かろうが遅かろうかかわらず、**トークンを焼けば実行は遅れる**。これで verbose な chain-of-thought が精度誤差とは別の独立した失敗モードとして計測可能になる。3つの能力軸は RT-Perceive（刻々と変わる世界状態を追えるか＝チケットはまだ売っているか）、RT-Deliberate（残時間に応じて推論深度を変えるか＝購入窓が閉じるなら考えるのをやめる）、RT-Act（買うべき瞬間に買えるか）。

- 課題構成: Web 30（travel / e-commerce / service / security）+ Game 20（arcade / puzzle / strategy / simulation）
- 参加モデル: GPT-6 Astra / GPT-5.6 Sol / GPT-Realtime-2 / OpenAI Decisions、Claude Fable 5.1 / Claude Opus 5、Gemini 3.8 Flash / 3.1 Flash Live / 3.8 Live、Jev 1.13、DeepSeek V4.1、Moonshot Kimi K3
- 首位は Import AI 479 の記載で **GPT-6 Astra (high) の Wall Clock 36%** — これは Pass^3 側の数値（abstract の best success は 44%）
- **reasoning effort を上げると time pressure 下では効果が混在** — 思考増＝窓を逃す。quality-timeliness トレードオフがベンチ数値として出た
- Jack Clark の位置づけ: 「AI エージェントがどこで壊れるかの実効プロキシ」。低いスコア＝无人委任してはいけない課題クラス（オークション、タイムセール、live game、first-come-first-served 全般）

## 実装側の独立証言 — Duet は4つの中で一貫して最速ではなく最遅

同じ結論が实验室の外から出ている。Claire Vo（chatprd.ai / *How I AI*）が 2026-11-02 に **Grok Bot / Dot / Meta Muse / Claude Duet** を9つの実務課題で比較した結果、**Duet は一貫して最遅**だった（Muse が9課題中4つで1位）。Vo の製品原則は「エージェントが数分消えると、ユーザーは文脈を失って使わなくなる」。

さらに Duet は承認を**4回**要求、他3エージェントは**全員1回**。[[concepts/duet-style-hierarchical-assistant]] の「decreasing-access hierarchy」（上位レイヤーは全業務を見渡せるが低レベルアクセスを持たない／チャンネルが実アクセス／sub-thread がサンドボックス内）という、[[concepts/capability-based-security]] 的に正しい設計の UX 請求書がこれだ。[[concepts/harness-engineering/agent-harness]] の一般的な設計（トップの planner が全 credential を握って下へ委任する）の逆をやった代償が、承認回数として可視化されている。

| 単位 | 遅延のコスト | 現れる場所 |
|---|---|---|
| ベンチ | Wall Clock 44% vs Paused 70–80% | RT-Deliberate 失敗（考えすぎて窓を逃す） |
| 製品 | 4エージェント中4位（一貫して最遅） | ユーザーが文脈を失って離脱 |
| 製品 | 承認 4回 vs 1回 | 「信頼」でなく「監視対象」として知覚される |

Duet の速さの主張自体が注意が必要だ。fig.blue の実践レビューは「同じ base model の他 Claude UI より明確に速い」と書くが、バックエンドは **Opus 5.5 固定で model/effort ピッカーなし**。つまり速さは tuned product/model pairing の結果であって、一般結果ではない。

## 深夜の設計含意 — CoT を「料金」ではなく「時刻」として設計する

[[concepts/test-time-compute]] の議論はこれまで「トークンを増やせば精度が上がる」の一方通行だった。Realtime-Bench はそこに反対の請求書を足す — **トークンは時刻を消費する**。[[concepts/token-economics]] の料金体系にレイテンシ課金が入る余地がある。RT-Deliberate の失敗は「賢くない」のではなく「予算配分ができない」ので、対策は推論量の増減ではなく**残時間を入力として推論深度を制御するループ**側にある。[[concepts/inference-speed-development]] の速さ＝使用可能性論は、ベンチで最遅だったエージェントの離脱データと、ベンチで最大のスコア差が出た時計条件の両方から同時に支持された格好だ。

## 今夜やるなら（15分）

realtimeagents.org のリーダーボードを開き、自分が運用しているエージェントの課題を1つ Wall Clock 想定で書き直してみる（例: 「在庫があるうちに注文する」）。RT-Perceive / RT-Deliberate / RT-Act のどれで落ちるかを切り分けると、[[concepts/reasoning-models]] の effort 設定を上げるべきか、ツール呼び出しの合間に観察を挟むべきかが分かる。effort を上げる前に確認したいのは「窓の長さ」だ。窓が短い課題で effort を上げると、このベンチのデータでは大抵マイナスになる。
