## 🏆 9.8 vs 8.0 — 勝ったのはモデルではなく1時間のループである

**▶ 一言要約**: LiveCodeBench Hard 上位10問×5回で、5体のQwen3.8-27Bチーム（Memdoor）は平均 **9.8/10**。Fable 5の単発呼び出しは **8.0**。ただし元の著者ハーネスは単一モデルで **9.6** — 差の大半はモデルではなくハーネス側にある。

**詳細**（出典: [raw: guregodevo/memdoor README](raw/articles/2026-10-31_github-memdoor-team-solve.md) / [HN 50320995](https://news.ycombinator.com/item?id=50320995)）:
- 数字の分解を先にやる。[[concepts/ai-benchmarks/livecodebench]] Hard の先頭10問、5パス平均で 9.8（Memdoor再構築）/ 9.6（著者自身のハーネス）/ 8.0（Fable 5、単発）。つまり「5×27B > frontier 1発」の見出しの裏で、**単一モデル+良ハーネス 9.6 ≒ 5体チーム 9.8** という並び
- 残差の正体は計算時間: 著者ハーネスのループは最難問で **100 token/sec 時に1時間超**。作者 guregodevo 自身「3.8-flash-next なら10点と最難問の高速化が見込める」と書いている。要は **wall-clock × 反復回数**がスコアを買っている
- 再現性の作り込みは本物: 全 **50 run** を公開（リクエスト・返信・プログラム・grader出力すべて）。ハーネスは **YAML** で記述されモデル名を指定しない — `memdoor connect local` で Ollama / llama.cpp / vLLM / LM Studio に切り替え可能。[[concepts/harness-engineering]] の「ハーネスが成果の主体」という主張の実演として成立している
- 反論も HN に立っている。@vikramkr「何年も前の飽和・汚染ベンチで、実務のエージェント作業を反映しない指標で、自作ハーネスを作って frontier に勝ったと言えば互联网ポイントがもらえる」— [[concepts/evaluation/llm-as-judge]] 界隈の「ベンチは主戦場ではない」論点の正しい適用例

**深掘り（なぜこの比較が危ういか）**: [[concepts/ai-benchmarks/livecodebench]] の存在意義は、LeetCode/AtCoder/CodeForces から継続的に新問を収穫し**訓練カットオフ後の問題だけで評価する**汚染防止設計にある（arXiv 2403.07974）。したがって Hard サブセットで「飽和・汚染」を主張するなら、問題IDと公開日、モデル側の訓練カットオフを併記しないと反論は未証明のまま。逆に「5体で frontier 超え」側も、Fable 5 に同じ 1 時間ループを与えた対照実験がない以上、主張できるのは *"single call"* 対 *"5-agent loop"* に限られる。同一モデル/同一予算で比較されていない 1.8 点は、モデル間差として読んでよい数字ではない。

## 局所実行の上限讨论 — Bonsai 2-bit は救世主か

**▶ 一言要約**: 「ゲーマー機で Qwen 27B を 50 t/s、局所で Fable 5 級」という HN の期待に対して、 quantization 経験者2名が **Bonsai 2-bit** の品質を明示的に否定した。

- @roenxi: Bonsai 2 量子化なら手頃なゲーミング機で Qwen 27B を **50 t/s** 達成可能 → 「局所性能の天井はかなり高い」。根拠は [[concepts/bonsai-27b]] の実測スペック — 1.125 bits/重み・3.9 GB、RTX 5090 で **163 tok/s**、M5 Max で **87 tok/s**、15 ベンチの性能維持率 **90%**（ternary 版 1.71 bits/5.9 GB は 95%）
- @SwellJoe 反論: 「Bonsai 2-bit quantization は 8-bit や 4-bit の Qwen 27B より明らかに鈍い。5体集めてもこの品質には届かないと思う」
- @Havoc 補足: 「5 GB の bonsai 重みは 5 GB の QAT 重みと同等程度。片方は 27B、片方は 8B 由来なのに」— つまり**バイト数で比べた瞬間に実効パラメータ数が落ちる**
- 技術的な含み: 9.8/10 に必要な反復を 50 t/s で回すと、最難問 1 問で数十分×5。[[concepts/local-llm/model-quantization]] の「2-bit は可能だが上限が下がる」教訓と、team-solve の「ループが時間を食う」制約は**積になって効く**。局所Fable 5級の壁は VRAM より先にレイテンシ budget 側にある
- @fedpost の文脈化: 「Anthropic がゲームのリバースエンジニアリングを制限した今、ハイパースケーラーに対して局所モデルを競争相手に保つ必要がある」。[[concepts/reverse-engineering]] の利用可否が局所モデル需要を押し上げる、という因果は [[concepts/frontier-model-usage-policy-enforcement-2026-10]] の 367 HN pts スレッドと同じ流れ

**深掘り（Cerebras の失敗は情報価値が高い）**: guregodevo は Cerebras も試したが **出力 32K 上限**で著者の 128K 推論予算が収まらなかった（「速度は本物」）。速い推論器であっても、長い思考ループを前提にしたハーネスの前提条件（出力トークン上限）に噛み合わなければ使えない。ハーネス設計上の制約条件として [[concepts/harness-engineering]] 側に記録しておく価値がある。

## 残る空白

- 「5体チーム vs frontier 1発」の対照実験（同一ハーネス・同一 wall-clock 予算）が存在しない。Memdoor は YAML を公開しているのだから、Fable 5 を同じ team-solve ワークフローに流した run が次の一手として最も費用対効果が高い
- 元の GVS5H ハーネスの 1 週間前のスレッドは [HN 50228167](https://news.ycombinator.com/item?id=50228167)。今回の 381 pts と併せると、"harness beats model" 系の投稿は継続的に 250〜400 pts を取っており、[[concepts/weight-compiled-computers]]（1 回の Opus 5.5 プロンプトで 15 年前の 6502 準拠テストスイートを自律発見した例）と同じ「古い決定論的テスト群をエージェントのオラクルに使う」パターン群として扱うべき
- 数値の性質を明示しておく: 9.8 / 9.6 / 8.0 と 50 run 公開は一次ソース（repo README、HN item 50320995、381 pts）からの転記であり、Hermes 側での再実行・再計算は行っていない。[[concepts/ai-benchmarks/agent-arena]] 系の独立再現待ち、という位置づけ
