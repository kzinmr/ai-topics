# 🏆 1スキル→5,000スキルを1年で運用したUberの数字 — skill fleet運用の実測値が公開された

朝イチの1本。[[concepts/agent-skills]] は2025年12月のAnthropic公開標準だが、「1万スキルをどう回すか」の公開事例は今まで無かった。Uberが2026-11-23に公開した "How Uber Evals 1 Million Agent Skill Invocations a Month" (X記事、ブックマーク21.5K) が初めてのフルケーススタディで、評価・コスト・バグ報告まで全部実数付き。wiki化済み: [[concepts/enterprise-skill-fleet-operations]]。

## 1. 評価設計 — 「pass率100%のevalはweak」

**▶ 一言要約**: eval suiteの構成は golden 5% / real-prompt trajectory採点 80% / 作者判定 15%。100%パスするevalは回帰を検出できないので疑え、というのがUberの運用則。

**詳細**:
- ゴールデンケース(固定入出力+tool mock)は全体のわずか5%。主力は実プロンプトのリプレイをtrajectoryで採点する80%枠
- 実行はクリーンルーム(Minion、AES sandbox、devpod)で。「動くのは自分のマシンだけ」依存をCI前に落とす
- Ablation実験の実数: warehouse-queryスキルを除去してリプレイすると tool calls +13%、tool errors **6倍**、所要時間 +31%。スキル版の回答はブラインド判定で87%勝った
- 追加で「スキル作者が判定する15%枠」を別建てにしているのが設計上の工夫。自動判定の盲点を人間側で受け持つ分担

## 2. コスト会計 — invocation単位でsession差分を取る

**▶ 一言要約**: invocationコスト = 呼び出し直前のsession合計 − 直後。スキル本文の読み込みと下流ターンまで課金に含める。計測で確定した削減レバーは4本。

| レバー | 削減幅(実測) |
|---|---|
| Code Mode化(決定的なフローをgatewayスクリプトへ) | [[concepts/code-mode]] 参照。>100 MCPツールpreload=50–70K tokensを削除 |
| 安価モデルのworker subagent化 | tracingスキル **−46%/invocation** |
| ロード時にscript実行 | searchスキル **−32%** |
| pollingのbackground agent化 | top-20 sessionの支出の**約1/3** |

**詳細**:
- OpenTelemetryフックで skill/version/agent選択かユーザー入力かを emission。プロンプト本文とファイル内容は送らない設計
- per-skill 12指標(users, retention, cost, latency, errors…)。all-or-nothingのダッシュボードではなくスキル単位P&L
- これは2026-06時点の「UberがAIツールコストに上限をかけた」報道([[raw/articles/simonwillison.net--2026-jun-3-uber-caps-usage--0437d797]])から1年半で、コスト管理が「上限」から「計装」に移ったことを意味する。広めの文脈は [[concepts/enterprise-ai-cost-management]]

## 3. アーキテクチャ — git repo 1個がregistryの代わり

**▶ 一言要約**: 1 Git repo + `aifx` CLI + 3層tier(Domain=peer 1承認+CI / Core=platform審査 / Always-on=~100)。公開エコシステムのregistry欠如へのUberの答えは「企業内蔵」だった。

**詳細**:
- [[concepts/agent-skill-ecosystem-missing-package-manager]] が計測した公開エコシステムの欠陥 — コピーネットワーク2,193,119 adoption、starsはコピー元を特定できない(audit上位100 repoで高リスクadoptionの14.9%を防止 vs stars上位100で0.5%、約30倍差) — に対し、Uberはgit履歴=provenance、owner制度=accountabilityで内部解決
- ただし同ページ自身が指摘する通り、これは市場外のスキルには一切効かない。package-manager問題の公域版は依然open
- config mergeは company→team→repo→directory→user→local の加算のみ6層。Claude Code/Codex/OpenCodeで同一スキルが動く
- スキルの名前の衝突解決が無い公開問題([[concepts/agent-skill-ecosystem-missing-package-manager]] の「install locationが勝者をdecide」)は、platformチームreviewのある内部では顕在化しにくい

## 4. エージェントが自分のバグを報告する — Papercuts

**▶ 一言要約**: always-onの `log-papercut` スキルが、エージェントに指示されず frictionレポート(tried/expected/happened/fix)を自動起票。3か月で数千件、数百件がfix済み。

**詳細**:
- fixの実例が地味に valuable: 共有temp file起因のcommit-message race、epoch秒 vs ミリ秒のunit bug、黙って別キーを引くconfig lookup、CIの無いrepoでCI待ちして404ループ
- 人間のシグナル(Fawkes運用でのコメント/却下PR)がeval setに還流する閉ループ
- 「1スキル→5,000+スキル/年、>1M invocations/month」のスケールでないと現れない故障モードのカタログが、このセクションの価値

## 読みどころの順番

1. 評価設計(100%パスを疑う)はそのまま自組織のeval designに転用可能
2. コスト4レバーはTableの数字だけを拾う読み方で十分
3. registry内蔵論は「公開エコシステムでは何が起きるか」の対照実験として読むと面白い
